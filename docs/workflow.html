Workflow

How work on Velatura is organised. Agreed with the owner on 2026-10-11 (decision D35).

1. Rules

  1. One branch and one pull request per phase. Branches are named phase-0-spikes, phase-1a-engine-cli, phase-1b-targets and so on.
  2. Nothing is committed, merged or pushed unless the tests pass. The gate is one command, scripts/check.sh. The same command runs in GitHub Actions on every pull request, and a pull request is merged only after that run is green.
  3. One changelog page per phase in docs/changelog/, written in the same pull request as the work.
  4. Docs are HTML in docs/, self-contained, and updated in the same pull request as the change they describe.
  5. The owner's live desktop is not touched without asking. Tests run in throw-away directories. Anything that would change the real home directory or session, including turning off the old theme timer, is asked first.

2. The test gate

scripts/check.sh runs, in order, and stops at the first failure:

  1. Formatting check (cargo fmt --check).
  2. Lints with warnings treated as errors (cargo clippy).
  3. All tests (cargo test).
  4. Documentation check: every HTML file parses, every internal link and anchor resolves, and no page loads anything from the network.

scripts/check-in-container.sh runs the same gate inside the Fedora container that GitHub Actions uses, with podman and without root. It is the way to run the full gate, including formatting, when a tool is missing on the host.

Later phases add steps to this one script (golden files, dependency audit, GTK stylesheet acceptance), so there is always exactly one gate.

3. Closing a phase

  1. The pull request description lists the phase's exit condition from the roadmap as a checklist, and states plainly anything that was not done or was moved to a later phase.
  2. The gate passes locally and in GitHub Actions.
  3. The pull request is squash-merged, so main has one commit per phase.
  4. main is tagged with the phase name, for example phase-0.
  5. The plan and decisions log are corrected where the phase showed an assumption to be wrong.

4. Releasing

  1. A pull request sets the new version in Cargo.toml (with Cargo.lock), and the changelog says what the release holds. On such a pull request the release workflow builds and checks everything, and publishes nothing.
  2. Once it is merged, main is tagged v<version> and the tag is pushed. The workflow refuses a tag that is not the version in Cargo.toml.
  3. The workflow builds the release on Fedora 41, installs and runs it, builds the source offline, and publishes the release with its files and SHA256SUMS.
  4. scripts/release.sh builds the same files locally, into dist/, for a look before tagging.

Pushing a tag publishes: it is done by the owner, or with the owner's go-ahead (D65).

5. Additions

All agreed with the owner and in place.

  • A single gate script shared by local runs and CI.
  • A tag per merged phase, so any phase can be checked out or compared later.
  • A written result for every experiment in Spike results, so a decision can be traced to its evidence.
  • main is protected on GitHub: it only accepts pull requests whose check passed, which makes rule 2 enforced by GitHub and not only by habit. Small changes that are not a phase, such as a docs correction, go through their own short pull request.
  • A short README.md that only points to the HTML docs.
  • docs/ is published with GitHub Pages at rafael0rueda.github.io/Velatura.
