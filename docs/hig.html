Interface guidelines

The GNOME Human Interface Guidelines, as they apply to Velatura. Read in full on 2026-10-12 from developer.gnome.org/hig: the principles, all eleven guidelines, the patterns Velatura uses, and the keyboard reference. This page is the working checklist for the GUI phase (1c) and for every user-facing text written before it, including the command line.

How this page is used. Section 2 lists what the reading changed in the plan. Sections 3 to 9 are rules to build by. Section 10 is the acceptance checklist that the GUI pull request must tick off. Where the guidelines and a safety requirement pull in different directions, the conflict is named and the decision is the owner's.

1. The four principles

PrincipleWhat it asksWhat it means here
Design for PeopleLittle specialist knowledge; all abilities, languages and device sizes.No file paths, CSS or setting keys in the main flow. They sit behind "Show Details". Works by keyboard alone, with a screen reader, in High Contrast and with large text.
Make it SimpleDo one thing well; reveal detail progressively; common actions close at hand.The app applies a theme. Pick a theme, press one button. The editor, history and per-app set-up are further away and never in the way of that.
Reduce User EffortAutomate; fewer steps; less to remember; short text.Apps are detected, not configured by hand. The nearest accent is chosen automatically. The theme in use is always marked. Any step left to the user (restart an app) comes with a copy button.
Be ConsideratePrevent mistakes; prefer undo to confirmation; do not interrupt.Every apply can be undone and the original setup restored. No dialog appears unless the user started the action. A scheduled switch never asks anything.

3. Window structure and navigation

  • One primary window, resizable, opening at a size that fits its content, and remembering its size.
  • Three top-level views in a view switcher: Themes, Apps & Desktop, History. Labels are nouns in header capitalisation. Three to five views is the range for a view switcher, so Phase 2 can add one before a sidebar is needed. Below the width where the switcher fits the header bar, it moves to a bar at the bottom edge.
  • One level of depth below a view: a theme page, an app page, the editor. Moving in and out uses the browsing pattern: back button at the top left, header bar title and controls change with the view, Alt+Left goes back.
  • Secondary windows only for Preferences, About, Keyboard Shortcuts and dialogs. Always attached to the main window, never stacked on one another, never larger than it.
  • Header bar: main actions at the start, title or view switcher in the centre, menus at the end. Few controls, free space left for dragging, a tooltip on every control. The primary menu button uses the standard menu icon and the tooltip "Main Menu", and is shown on top-level views only.
  • Content width is capped so lists and text do not stretch across a wide window.
  • Sizes to hold: 360×294 for narrow, 1024×600 as the smallest desktop screen. Layout changes at a breakpoint are animated, and nothing jumps or vanishes.

5. Writing

  • US English in source strings. Short. Neutral. No "you" or "my"; "your" only where ownership has to be said.
  • Words the user knows: app, backup, settings file. Never target, snapshot, managed block, dconf, GSettings or CSS in the main flow. The vocabulary table in the architecture stays the reference.
  • Header capitalisation for headings, view titles, buttons, switch labels, menu items and tooltips: "Apply Theme", "Stop Theming", "Restore Original Setup".
  • Sentence capitalisation for body text, descriptions, check box and radio labels, drop-down labels and items.
  • Headings are not sentences: "Theme Applied", not "The Theme Has Been Applied". Toasts and banners use the informal form: "Theme applied", "High Contrast is on".
  • Ellipsis (the single character …) on a label when more input or a confirmation follows: "Import…", "Restore…". Not on "Preferences" or "About Velatura".
  • No full stop at the end of a heading, a label or a single-sentence description. Full stops only between sentences.
  • Buttons are imperative verbs: Apply, Restore, Undo, Import. No OK, Yes or Done as the affirmative.
  • Typography: curly quotes and apostrophes, × for dimensions, an en dash for ranges, a narrow no-break space before a unit. No all-capitals, no italics, no hard-coded fonts or sizes; the standard text styles only.
  • Translation: no sentence built across several controls; no "e.g." or "i.e."; access keys are part of the translated string.
  • No device words: "select", not "click"; nothing essential shown only on hover; no double-click or right-click actions without another way to reach them.

For the command line (Phase 1a onward). The guidelines are written for windows, but the writing rules carry over: US English, short neutral sentences, the same vocabulary as the GUI, a plain statement of what was changed and how to undo it.

  • Only standard shortcuts are used. No Alt or Super combinations of the app's own.
  • Undo Last Apply is off while a text field has the focus or the theme editor is open: GTK hands a key to the window's shortcuts before the focused widget, so Ctrl+Z would otherwise undo the desktop instead of the typing.
  • Unsaved work in the editor is never lost without asking: Back, Esc, Alt+Left, opening another theme in the editor, closing the window and Quit all ask "Discard Changes?" first.
  • Every labelled control has an access key; no letter repeats inside one dialog or menu; thin letters and letters with descenders are avoided.
  • Everything is reachable with Tab and the arrow keys in a sensible order. Return activates, Space toggles, Esc closes dialogs, popovers and menus.
  • In a list of rows with controls, focus goes to the controls.

7. Style and colour

  • The app follows the system light or dark style. It has no style preference of its own.
  • Built-in style classes and colour variables only, each for its intended purpose: suggested for Apply Theme, destructive for Apply Anyway and for removing a generated folder, the standard title and caption text styles.
  • One suggested or destructive button per view.
  • The stylesheets of its own are the stock-colours exception (H7), the scoped colours of the preview, and a few rules libadwaita has no class for (D72): the outline of the theme card in use, the tile behind a part's icon, the tags beside a part's name, and the dimmed name of a part that cannot be themed. Those rules use named colours only.
  • A theme's colours appear only in swatches and in the preview. A swatch always has its name and value as text beside it or as its accessible name.
  • No flashing or blinking. No text drawn over images.
  • Interface icons are symbolic and taken from the existing sets before any is drawn. A control has an icon or a label, not both, except in the view switcher and the buttons beside the theme cards, in Day and Night and in History, which have both (D72). Icon-only buttons are limited to icons people already know: menu, search, back.

8. Accessibility

  • Every control and every swatch has a short accessible name.
  • The whole app can be used with the keyboard alone, and with the screen reader with the display off.
  • Correct in High Contrast and with large text; no label cut off.
  • Text entries work with the on-screen keyboard.
  • Targets are large enough for touch; a row can be activated anywhere on its surface.

9. Name and icon

  • Name: "Velatura", capitalised, in every title, menu and store entry.
  • App icon: one simple object tied to the name. Since D72 a fan of three paint chips pinned at one point, each topped with a theme colour (red, orange, blue), on a lit violet tile over a darker base edge: slight depth, flat colours on flat surfaces, and no shadow outside the outline. It must read at 64 and 32 px.
  • Symbolic icon: the same fan as outlines, in one colour on the 16 px grid. Filled paths only, with the two chips behind cut at the front one's edge: GTK 4.22 draws symbolic icons itself and ignores clip paths, and older GTK fills every shape.
  • Development builds get the nightly variant so they are not mistaken for a release.
  • Checked with App Icon Preview and Symbolic Preview. Neither is installed yet; both are available as Flatpaks and will be asked for before Phase 1c.

10. Acceptance checklist for the GUI phase

The Phase 1c pull request copies this list into its description and ticks each line, or states why a line is not met.

  1. Primary menu holds, last and in this order: Preferences, Keyboard Shortcuts, Help, About Velatura. No Quit.
  2. Every header bar control has a tooltip. No label-only or suggested button in the header bar.
  3. At most one suggested or destructive button per view.
  4. No list row holds more than two controls.
  5. Every dialog was opened by a user action, has the main window as parent, puts Cancel first, and names its action with a verb.
  6. No error dialog where a toast or the result page will do.
  7. Every destructive action can be undone, or is confirmed where undo is impossible.
  8. All shortcuts are from the standard set and are listed in the Keyboard Shortcuts window.
  9. All labelled controls have access keys with no conflicts, in English and Spanish.
  10. Text follows section 5: capitalisation, ellipsis, full stops, typography, no "you" or "my", no internal terms.
  11. Usable at 360×294 and at 1024×600; content capped on a wide window; window size remembered.
  12. Passes in High Contrast, with large text, with the screen reader, with the keyboard alone, and with animations off.
  13. No status carried by colour alone.
  14. No custom styling beyond the three recorded exceptions.
  15. App icon and symbolic icon follow section 9.
  16. A right-to-left run and a pseudo-locale run show no broken layout.
