Theming targets and how each is applied

Revision 2, corrected after the platform review. Official uses a documented, supported mechanism. Workaround works today but is not promised by the upstream project and can break on an update. Not feasible cannot be done within the project's rules. Results of the Phase 0 experiments are in Spike results.

2. Dark style and accent colour

These two settings are the only appearance controls GNOME officially offers to libadwaita apps. The app sets the dark style from the theme's appearance, and the accent to whichever of the nine system accents (blue, teal, green, yellow, orange, red, pink, purple, slate) is perceptually closest to the theme's accent. The theme page shows both: "Accent: theme colour; fallback: Purple (system)".

  • Apps that ignore the workaround below show the nearest system accent, not the exact theme accent. Since Phase 4b the Shell shows the exact one (section 5).
  • Browsers and Electron apps read these two settings through the desktop portal, so they follow the dark style and system accent with no further work.
  • The legacy file gtk-3.0/settings.ini may force a dark preference (it does on this machine) and would fight a light theme; the app reports it.

3. GTK4 and libadwaita

How it is applied. The app creates ~/.config/gtk-4.0/velatura.css and connects it with one @import line at the end of the user's ~/.config/gtk-4.0/gtk.css. The file redefines libadwaita's named colours (window_bg_color, headerbar_bg_color, accent_bg_color and the rest), sets the few newer colours that exist only as CSS variables, and sets the plain GTK names used by GTK4 apps without libadwaita.

Verified on libadwaita 1.9: the user's gtk.css is loaded at a higher priority than libadwaita's stylesheet, its system-accent definitions and app stylesheets, so the overrides win. Redefining the named colours also drives the matching CSS variables. The same on 1.6 to 1.8 is to verify.

Limitations:

  • libadwaita does not support themes. Its developers consider this recolouring unsupported, and apps are tested only against the stock look. Bug reports must not go to app developers while a theme is active.
  • Only colours change. Shapes, spacing and icons stay as libadwaita defines them.
  • Apps that hard-code colours or draw their own content keep those colours.
  • Running apps do not pick up the change. GTK reads the file once at start.
  • Existing definitions can override the theme. Definitions later in the user's own gtk.css win over an import placed at the top. This machine's file has about 60 such lines, as does any file left by Gradience. The app detects this and reports the target as "set up but not taking effect". Resolved in Phase 0: the connection line is placed at the end of gtk.css, where GTK accepts it and it wins over earlier definitions. Lines added by the user after it are still detected and reported.
  • High Contrast. The overrides stay active when High Contrast is on, which would reduce contrast. The app therefore skips GTK recolouring while High Contrast is on, and warns if it is turned on later.
  • Title bars of X11 apps are drawn by a helper that reads this file once at login, so they change only at the next login.
  • Flatpak apps use the GTK of their runtime. Newer syntax (colour-scheme media queries need GTK 4.20) cannot be assumed; the file contains plain definitions for the current theme first.
  • The colour names may change in a future libadwaita, and a major version could remove the mechanism.

4. GTK3

Recommended method. Use adw-gtk3, a GTK3 theme that imitates libadwaita and accepts the same named colours (confirmed in Phase 0 with version 6.5). With it, one palette drives GTK3 and GTK4 and the two look alike.

There is no useful fallback without it. The stock GTK3 Adwaita theme has its colours compiled in: it defines the colour names but its widget rules do not use them, so overriding them changes almost nothing. The first plan's "Basic" mode was wrong and is removed. (The existing setup on this machine works around this with a hand-written GTK3 theme that repaints widgets one by one; that approach is not general.)

  1. The app looks for adw-gtk3 in the system and per-user theme directories.
  2. If found: it sets gtk-theme to adw-gtk3 or adw-gtk3-dark and connects a colour file from ~/.config/gtk-3.0/gtk.css. The previous gtk-theme value is backed up.
  3. If not found: GTK3 is shown as an optional set-up row, "Improve older apps", and is skipped. The row explains the per-user install into ~/.local/share/themes, which needs no root and also works on immutable systems, and mentions the distribution package where one exists. A built-in installer with a pinned version and checksum is considered for Phase 2.

Flatpak GTK3 apps cannot see a per-user copy of the theme; they need the matching Flatpak theme extension (org.gtk.Gtk3theme.adw-gtk3 and -dark), which Flatpak fetches by itself for the active GTK theme when it is available.

5. GNOME Shell

GNOME has no supported way to theme the Shell. Loading a custom Shell stylesheet requires the User Themes extension, which is maintained by GNOME but is still an extension and is often not enabled. On this machine it is installed per user and disabled, with a leftover theme name set.

Method A: User Themes (Phase 1d)

Verified in the Shell and extension sources for GNOME 47 to 50:

  • A user theme is layered over the stock stylesheet; it does not replace it. The generated theme therefore holds colour declarations only. It never imports the stock stylesheet or copies its sizes, shapes or spacing, and High Contrast is left alone. This also means a theme left over after a GNOME upgrade cannot break the Shell's layout.
  • What it holds (Phase 4b, D61). GNOME Shell 47 and later name the accent in their own stylesheet as -st-accent-color, and work out every shade while they run with st-mix, st-lighten, st-darken and st-transparentize. Velatura reads that stylesheet, light or dark as the theme is, out of the installed Shell's bundle (gnome-shell/gnome-shell-theme.gresource under the system's data folders, read by a small reader of its own), and restates every declaration that holds a colour, about 560 rules, with the colours replaced: the accent by the theme's own; the Shell's greys by the colour at the same place on the theme's line from background to text (its darkest background for black, so the top bar is that); red, yellow and green by the theme's error, warning and success colours. The Shell's own functions stay, so every hover, focus and pressed shade keeps its place. The panel's text colour is stated outright, since the Shell's stylesheet lets it come down from the stage.
  • Where the stylesheet cannot be read, in Ubuntu's own session (whose Shell draws with Yaru) or with a damaged or missing bundle, the short list of earlier phases is written instead: the main surfaces in the theme's colours, the accent the nearest system one. The result says so.
  • The Shell reloads only when the theme name changes. Rewriting the file under the same name does nothing. Each apply therefore writes a new folder, ~/.local/share/themes/Velatura-<hash>/gnome-shell/gnome-shell.css, then sets the name; older generated folders are cleaned up.
  • Stylesheets of enabled extensions always win over the user theme, whatever the selector. An extension that styles the panel (several are enabled here) will override the theme there. An extension counts as winning when its stylesheet has a rule that starts on the top bar, a menu, quick settings, the calendar, a notification or the overview, and sets a colour; rules for its own widgets, or that apply only under a class of its own, do not. Then the top bar is reported as set up but not taking effect, with those extensions named, and Velatura's own extension suggested, which wins over them.
  • Order of steps: write the file, set the name, and only then ask the Shell to enable the extension, so a stale theme name is never shown.
  • The setting lives in the extension's own schema directory when installed per user, which the engine must look up explicitly.

Installing User Themes without root: the app asks GNOME Shell's own installer, which shows the Shell's confirmation dialog, downloads from extensions.gnome.org and enables it without a logout. This needs a network connection and can be disabled by an administrator; the app checks and explains. It never blocks the rest of an apply.

Method C: companion extension (Phase 2)

  • A minimal extension owned by this project loads one stylesheet written by the app and reloads it when the file changes. Because it competes at the same priority as other extensions, it can theme areas that Method A loses to them.
  • Published on extensions.gnome.org it installs without a logout. Installed from a local file, it needs a logout on install and on every update, since the Shell cannot restart under Wayland. All changing content therefore lives in the stylesheet, never in the extension's code.

Limitations

  • Colours the Shell does not write in its stylesheet are not reached: its few pictures (the dot under a calendar day with events, the welcome logo, the placeholder for an empty workspace) and colours other extensions set.
  • A Shell update brings a new stylesheet; the next apply restates it. Until then the theme written for the earlier one stays, and since it holds colours only, at worst some new parts keep their stock colours.
  • Per-version maintenance. Selectors change with every GNOME release. A static test checks each override against the stock stylesheet of each supported version.
  • High Contrast: Shell recolouring is skipped while it is on.
  • The lock screen and login screen keep the stock look.
  • One syntax error makes the Shell reject the whole stylesheet and fall back to the stock look (confirmed in Phase 0). The generated stylesheet is therefore syntax-checked before it is installed.

6. Flatpak apps

  • GTK apps in Flatpak cannot see ~/.config/gtk-3.0 or gtk-4.0. The app offers to add read-only access to those two directories by editing Flatpak's per-user override file, ~/.local/share/flatpak/overrides/global, as a key-level edit. Entries that were already there (both are, on this machine) are recorded as not the app's and are never removed.
  • This slightly widens every sandbox, read-only, so it is opt-in and explained. It can be granted per app instead.
  • Icon sets in ~/.local/share/icons are already visible to Flatpak apps. Sets in the legacy ~/.icons are not, so generated sets are always installed to the former.
  • Flatpak apps that are not GTK (Electron, Qt) are not affected.

7. Terminals

Kitty

  • The app creates ~/.config/kitty/velatura.conf and connects it with one include line at the end of kitty.conf, which is how Kitty's own theme tool works.
  • Things that override it, detected and reported: colour lines after the include; and Kitty's automatic theme files (dark-theme.auto.conf and its siblings), which override every colour setting. This machine has one, so the include alone would have no effect here.
  • Kitty's automatic theme files are not used as a connection method: their names are fixed, so they cannot be files the app owns, and they reset every colour the theme does not set.
  • Recent Kitty reloads its configuration by itself; on older versions the user presses Ctrl+Shift+F5.

Ghostty

  • The app creates ~/.config/ghostty/velatura.conf and connects it with one line, config-file = velatura.conf, in a marked block at the end of Ghostty's settings file (either of its two file names). Ghostty loads such a file after the whole settings file that names it, so its colours win over a theme line and over colour keys anywhere in the user's file. Changed in Phase 1b from the first plan, which used a theme file and lost to both (D41).
  • Detected and reported: another config-file line after the block, which is the one thing that can override it.
  • The user reloads with Ctrl+Shift+Comma.

8. Icons, cursors, wallpaper, fonts

  • Selection of any installed icon theme, cursor theme, wallpaper or font is a plain settings change. The app sets both the light and the dark wallpaper keys. On Wayland some apps show a new cursor theme only after restarting.
  • Icon recolouring (Phase 3d, off until turned on) builds a per-user icon theme, ~/.local/share/icons/Velatura-<theme>-<hash>/, that inherits from the icon theme in use and holds recoloured copies of the icons that carry its own colour: the shades of the colour its folder icons are drawn in, each moved to the theme's accent with its lightness relative to the main one kept. App icons are not touched, nor icons named …-symbolic, which follow the text colour; since D69 that is decided per icon, so an icon with a colour of its own in a folder named symbolic is recoloured. The set is hidden from lists of icon themes, and its name changes with its content, because GTK reloads an icon theme only when the name changes. The sets used last are kept, three of each kind besides the one in use, so going back to recent colours uses a set again at once; older ones are removed by an apply with someone present, never by a scheduled switch (D67). The app shows a page with a spinner while it prepares and applies a theme, which is when a set is made, and says after it that open apps show the icons once reopened, and everything after signing out and in. Since Phase 4d an icon theme made of pictures is recoloured too (D63): the family is the hue most of its folder pictures' coloured pixels share, its main colour the one they are filled with, and every pixel of that hue moves to the accent the way a shade does in a drawing, pixels at the family's edge part of the way, so edges stay smooth. Pictures are read and written as PNG by Velatura's own code over miniz_oxide for the compression. Monochrome symbolic icons already follow the text colour. In a theme made of pictures, its drawn icons (such as those for the top bar) move by the same family.
  • Cursor recolouring (Phase 4d, off until turned on, experimental; D64) builds a per-user cursor theme, ~/.local/share/icons/Velatura-cursors-<theme>-<hash>/, from the one in use, and sets the cursor to it. Every cursor's pictures are recoloured in place in its Xcursor file: greys along the line from the darker of the theme's background and text to the lighter, so a black body becomes the darker and a white outline the lighter, with the contrast between them the theme's text has; coloured parts, such as a busy spinner, become the accent's hue at their own lightness. A cursor with several names is copied under each, since a name the set lacked would be found in the original. Earlier sets are kept and cleared as icon sets are (D67).

9. Other applications

Neovim (Phase 3a)

The app creates a self-contained colourscheme, ~/.config/nvim/colors/velatura.lua, defining the standard highlight groups, Tree-sitter and diagnostic groups, common plugin groups and terminal colours, with no plugin dependency. Unless the settings already choose it, a marked block at the end of init.lua (or init.vim) holds one line that chooses it once Neovim has started, nested, so the user's own ColorScheme autocommands run as before and nothing else in the settings changes (D68). For people who keep their own colourscheme, the app also writes the same colours as a table, lua/velatura/palette.lua, for them to feed into it.

  • The first time, in a settings folder that already exists, the app asks before putting its two files there, and again before it first adds the line to the user's init.lua, even where Neovim was agreed to before; a scheduled switch never does either by itself.
  • To see what the settings choose, init.lua or init.vim and the Lua and Vim files under lua, plugin and after are read (a bounded number, comments passed over). Until the line is there, the part is shown as set up but not taking effect, with the colourscheme the settings choose.
  • The colourscheme loads itself again in an open Neovim when Velatura has rewritten it, the next time the window is focused.
  • Colours for code that a theme does not give are taken from its terminal and interface colours.
  • Only ~/.config/nvim is used; NVIM_APPNAME is not looked at.
  • Importing a theme from a running Neovim was proposed and is dropped for now, because it would mean running an external program against user configuration.

Starship (Phase 3a)

Starship supports named palettes but has no include mechanism, so the palette goes into starship.toml itself (or the file STARSHIP_CONFIG names): a marked block at the top of the file holding palette = "velatura" and the palette's colours as keys of the file's root (palettes.velatura.accent = …), leaving everything else byte-identical. Root keys must come before the first table, which is why this block is at the top and not at the end.

  • The palette has the seventeen interface roles under their names in the theme file, and directory, git and language, which a theme can set under slots.starship. Where it does not, they are its terminal cyan, magenta and green, which many themes have alike, so a theme of one's own reads best with its own; both bundled themes set them.
  • The prompt only changes where the user's format strings use the palette's colour names. Starship's own colour names (red, bold cyan) are not redefined: they stay the terminal's.
  • A file that already selects a palette is left alone, with the reason: its prompt is written for that palette's names. So is a file that does not parse.

tmux (Phase 3a)

A file the app creates, ~/.config/tmux/velatura.conf, loaded by one source-file -q line in a marked block at the end of the user's settings. tmux reads ~/.tmux.conf and then tmux.conf in its settings folder; the block goes into the second when it exists, and into the first when that is the only one.

  • It sets fourteen style options present since tmux 2.9: status line, window list, pane borders, messages, copy mode, clock.
  • Detected and reported: lines after the block that set one of those options or load another file.
  • Colours written as text inside status-left, status-right or window formats are the user's and stay. Themes drawn by tmux plugins are not detected.
  • Running sessions keep their colours until the user loads the settings again; the app gives the command.

Ptyxis (Phase 3c)

Ptyxis reads palettes from ~/.local/share/org.gnome.Ptyxis/palettes/. The app creates velatura.palette there, with a light and a dark set that both hold the theme's colours (text, background, cursor, sixteen terminal colours), and sets the palette setting of the default profile to velatura. A profile's settings live at a path made of its id.

  • Only the default profile is set. Another profile may have its palette on purpose; the palette is there to choose for it.
  • The first change is made only when agreed to, never by a scheduled switch alone.
  • Ptyxis offers no way to ask what colours it shows, and its own import checks nothing. The generated file is compared with a palette from inside the installed Ptyxis.
  • A Ptyxis installed as a Flatpak app is not reached.

GNOME Text Editor (Phase 3c)

The app creates a GtkSourceView style scheme, ~/.local/share/gtksourceview-5/styles/velatura.xml, and sets Text Editor's style-scheme to velatura. The scheme covers the view, the styles languages build on, text with markup and a few languages by name, and says whether it is light or dark.

  • The first change is made only when agreed to.
  • Every app that shows code with GtkSourceView 5 finds the scheme in its list; only Text Editor is set to it.
  • Text Editor's own light or dark look follows the desktop's style and is not changed.
  • An open Text Editor shows a rewritten scheme once reopened.

Firefox (Phase 4a, experimental)

  • In the profile Firefox opens by default, as installs.ini names it (the one marked Default=1 for an older Firefox): a stylesheet the app creates, chrome/velatura.css; a marked block with its import at the top of chrome/userChrome.css, since an @import must come before every rule; and a marked block at the end of user.js with the line that turns on toolkit.legacyUserProfileCustomizations.stylesheets, the preference that makes Firefox read userChrome.css. Other profiles are left as they are, and that is said (D60).
  • Profiles are looked for in ~/.mozilla/firefox, then ~/.config/mozilla/firefox, where newer versions start, then the Flatpak's and the Snap's folders.
  • The stylesheet sets 39 of Firefox's own design variables on the window's root, and its colour scheme: the tab strip, toolbar, address field and its results, menus and panels, sidebar, and the accent. Nothing else, so a variable a newer Firefox no longer reads does nothing. A user stylesheet's ordinary declarations lose to Firefox's own, so each one is !important. A test checks every variable against the list Firefox's own stylesheets read, taken from each version checked.
  • Off until turned on, and the first change needs agreement, because the profile is the user's. A scheduled switch never starts theming Firefox by itself.
  • Mozilla does not support this mechanism and Firefox releases every four weeks, so it is the most fragile target. Rules of the user's in userChrome.css that set the same variables, and a line after the block that turns the preference off, win and are reported.
  • Written while Firefox runs: it reads these files only when it starts and never writes them. Its own settings file, prefs.js, is never touched. Firefox shows the change after it is restarted.
  • Not fully reversible: once Firefox has read the preference it keeps it in its own settings; removing the line does not turn it off. Undo and Remove Everything say so, with the setting to change in about:config. With the import gone it has nothing of Velatura's to read.

Templates of the user's (Phase 4c)

For an app Velatura does not know, a template: a TOML file in ~/.local/share/velatura/templates/ that names where its output goes and holds its text (D62).

schema = 1
name = "Foot"
output = "~/.config/foot/colors.ini"
template = '''
[colors]
background={{bg|bare}}
foreground={{fg|bare}}
regular1={{red|bare}}
'''
  • Placeholders are {{name}} or {{name|format}}. Names: the interface roles (bg, fg, accent, surface and the rest), the sixteen terminal colours (black to bright_white), syntax.<role>, diff.<role>, diagnostic.<role>, and appearance, the word dark or light. Formats: hex (#rrggbb, the default), bare (rrggbb), rgb (224, 145, 79) and float (0.878, 0.569, 0.310). Nothing else: no conditions, loops or includes, and nothing of a theme file but its colours reaches the output.
  • A {{ without a placeholder's shape is text, so code that holds one is left alone. One with the shape that names something unknown is refused, with its line, so a misspelt name is never written out.
  • Where the output may go. A template's text is written as it is, so a template is as trustworthy as a settings file from wherever it came from. Its output must be a file under ~/.config/ (the settings folder) or ~/.local/share/ (the data folder), and not in a folder programs are started from: autostart, systemd and environment.d in the first; applications, dbus-1, systemd, gnome-shell, nautilus, flatpak and kservices5 in the second; nor Velatura's own folders, nor any name that starts like Velatura's own files. Velatura creates and owns that file, makes the folders it needs, and never writes over a file it did not make. Two templates may not write one file.
  • Taking part. A template takes part in every apply and switch once it is added, and can be turned off on Apps & Desktop under Templates or with --except. Its first write is made only when agreed to, so a scheduled switch never starts one by itself.
  • Managing. velatura template add <file> checks a template and copies it in (--as for another id, --replace to replace one); velatura template lists them with where each writes, or why one cannot be used; velatura template remove <id> takes one out and keeps a copy. The file a removed template wrote stays, as a part's files do when it is turned off, until Undo or Remove Everything takes it away.
  • Connecting the output to its app (an include line in its settings, say) is the user's to do.

Qt apps through a template (Phase 4e)

Qt apps take colours from a platform theme, such as qt6ct or Kvantum, which needs its own package and a session variable telling Qt to use it. Velatura installs no package and sets no session variable (D66), and Qt 6 apps already follow the dark style through the desktop portal. For full colours, a template for qt6ct comes with Velatura, in each release as templates/qt6ct.toml and here; a test keeps it in step with what Velatura accepts. qt6ct itself was not run with it.

10. Not feasible or deferred

  • GDM login screen and lock screen.
  • Qt apps have no built-in part (D66); see Qt apps through a template.
  • Obsidian: left out by decision (D54). It was planned as a CSS snippet written into each vault the user chose.
  • Title bars of apps that draw their own (Kitty, Electron apps): GNOME does not draw title bars for Wayland apps.
  • Apps with hard-coded colours, and Electron or Chromium apps without their own theme mechanism.
  • Restyling of libadwaita apps beyond colour: not possible by design.
