2. Dark style and accent colour

These two settings are the only appearance controls GNOME officially offers to libadwaita apps. The app sets the dark style from the theme's appearance, and the accent to whichever of the nine system accents (blue, teal, green, yellow, orange, red, pink, purple, slate) is perceptually closest to the theme's accent. The theme page shows both: "Accent: theme colour; fallback: Purple (system)".

  • GNOME Shell, and apps that ignore the workaround below, show the nearest system accent, not the exact theme accent.
  • Browsers and Electron apps read these two settings through the desktop portal, so they follow the dark style and system accent with no further work.
  • The legacy file gtk-3.0/settings.ini may force a dark preference (it does on this machine) and would fight a light theme; the app reports it.

3. GTK4 and libadwaita

How it is applied. The app creates ~/.config/gtk-4.0/velatura.css and connects it with one @import line at the end of the user's ~/.config/gtk-4.0/gtk.css. The file redefines libadwaita's named colours (window_bg_color, headerbar_bg_color, accent_bg_color and the rest), sets the few newer colours that exist only as CSS variables, and sets the plain GTK names used by GTK4 apps without libadwaita.

Verified on libadwaita 1.9: the user's gtk.css is loaded at a higher priority than libadwaita's stylesheet, its system-accent definitions and app stylesheets, so the overrides win. Redefining the named colours also drives the matching CSS variables. The same on 1.6 to 1.8 is to verify.

Limitations:

  • libadwaita does not support themes. Its developers consider this recolouring unsupported, and apps are tested only against the stock look. Bug reports must not go to app developers while a theme is active.
  • Only colours change. Shapes, spacing and icons stay as libadwaita defines them.
  • Apps that hard-code colours or draw their own content keep those colours.
  • Running apps do not pick up the change. GTK reads the file once at start.
  • Existing definitions can override the theme. Definitions later in the user's own gtk.css win over an import placed at the top. This machine's file has about 60 such lines, as does any file left by Gradience. The app detects this and reports the target as "set up but not taking effect". Resolved in Phase 0: the connection line is placed at the end of gtk.css, where GTK accepts it and it wins over earlier definitions. Lines added by the user after it are still detected and reported.
  • High Contrast. The overrides stay active when High Contrast is on, which would reduce contrast. The app therefore skips GTK recolouring while High Contrast is on, and warns if it is turned on later.
  • Title bars of X11 apps are drawn by a helper that reads this file once at login, so they change only at the next login.
  • Flatpak apps use the GTK of their runtime. Newer syntax (colour-scheme media queries need GTK 4.20) cannot be assumed; the file contains plain definitions for the current theme first.
  • The colour names may change in a future libadwaita, and a major version could remove the mechanism.

4. GTK3

Recommended method. Use adw-gtk3, a GTK3 theme that imitates libadwaita and accepts the same named colours (confirmed in Phase 0 with version 6.5). With it, one palette drives GTK3 and GTK4 and the two look alike.

There is no useful fallback without it. The stock GTK3 Adwaita theme has its colours compiled in: it defines the colour names but its widget rules do not use them, so overriding them changes almost nothing. The first plan's "Basic" mode was wrong and is removed. (The existing setup on this machine works around this with a hand-written GTK3 theme that repaints widgets one by one; that approach is not general.)

  1. The app looks for adw-gtk3 in the system and per-user theme directories.
  2. If found: it sets gtk-theme to adw-gtk3 or adw-gtk3-dark and connects a colour file from ~/.config/gtk-3.0/gtk.css. The previous gtk-theme value is backed up.
  3. If not found: GTK3 is shown as an optional set-up row, "Improve older apps", and is skipped. The row explains the per-user install into ~/.local/share/themes, which needs no root and also works on immutable systems, and mentions the distribution package where one exists. A built-in installer with a pinned version and checksum is considered for Phase 2.

Flatpak GTK3 apps cannot see a per-user copy of the theme; they need the matching Flatpak theme extension (org.gtk.Gtk3theme.adw-gtk3 and -dark), which Flatpak fetches by itself for the active GTK theme when it is available.

5. GNOME Shell

GNOME has no supported way to theme the Shell. Loading a custom Shell stylesheet requires the User Themes extension, which is maintained by GNOME but is still an extension and is often not enabled. On this machine it is installed per user and disabled, with a leftover theme name set.

Method A: User Themes (Phase 1d)

Verified in the Shell and extension sources for GNOME 47 to 50:

  • A user theme is layered over the stock stylesheet; it does not replace it. The generated theme is therefore a short list of colour overrides only. It never imports or copies the stock stylesheet, which would override the Shell's own light and high-contrast variants. This also means a theme left over after a GNOME upgrade cannot break the Shell's layout.
  • The Shell reloads only when the theme name changes. Rewriting the file under the same name does nothing. Each apply therefore writes a new folder, ~/.local/share/themes/Velatura-<hash>/gnome-shell/gnome-shell.css, then sets the name; older generated folders are cleaned up.
  • Stylesheets of enabled extensions always win over the user theme, whatever the selector. An extension that styles the panel (several are enabled here) will override the theme there. Troubleshooting lists enabled extensions that ship a stylesheet.
  • Order of steps: write the file, set the name, and only then ask the Shell to enable the extension, so a stale theme name is never shown.
  • The setting lives in the extension's own schema directory when installed per user, which the engine must look up explicitly.

Installing User Themes without root: the app asks GNOME Shell's own installer, which shows the Shell's confirmation dialog, downloads from extensions.gnome.org and enables it without a logout. This needs a network connection and can be disabled by an administrator; the app checks and explains. It never blocks the rest of an apply.

Method C: companion extension (Phase 2)

  • A minimal extension owned by this project loads one stylesheet written by the app and reloads it when the file changes. Because it competes at the same priority as other extensions, it can theme areas that Method A loses to them.
  • Published on extensions.gnome.org it installs without a logout. Installed from a local file, it needs a logout on install and on every update, since the Shell cannot restart under Wayland. All changing content therefore lives in the stylesheet, never in the extension's code.

Limitations

  • The accent is the system accent. The stock stylesheet uses the accent in about 200 places through colour functions, and the Shell's style language has no variables. An exact theme accent would mean restating all of those rules for every Shell version; it waits for Phase 4.
  • Coverage is partial. Overrides reach the main surfaces (panel, menus, quick settings, calendar and notifications, dash, overview, on-screen displays, switchers, dialogs) but not every derived shade.
  • Per-version maintenance. Selectors change with every GNOME release. A static test checks each override against the stock stylesheet of each supported version.
  • High Contrast: Shell recolouring is skipped while it is on.
  • The lock screen and login screen keep the stock look.
  • One syntax error makes the Shell reject the whole stylesheet and fall back to the stock look (confirmed in Phase 0). The generated stylesheet is therefore syntax-checked before it is installed.

6. Flatpak apps

  • GTK apps in Flatpak cannot see ~/.config/gtk-3.0 or gtk-4.0. The app offers to add read-only access to those two directories by editing Flatpak's per-user override file, ~/.local/share/flatpak/overrides/global, as a key-level edit. Entries that were already there (both are, on this machine) are recorded as not the app's and are never removed.
  • This slightly widens every sandbox, read-only, so it is opt-in and explained. It can be granted per app instead.
  • Icon sets in ~/.local/share/icons are already visible to Flatpak apps. Sets in the legacy ~/.icons are not, so generated sets are always installed to the former.
  • Flatpak apps that are not GTK (Electron, Qt) are not affected.

7. Terminals

Kitty

  • The app creates ~/.config/kitty/velatura.conf and connects it with one include line at the end of kitty.conf, which is how Kitty's own theme tool works.
  • Things that override it, detected and reported: colour lines after the include; and Kitty's automatic theme files (dark-theme.auto.conf and its siblings), which override every colour setting. This machine has one, so the include alone would have no effect here.
  • Kitty's automatic theme files are not used as a connection method: their names are fixed, so they cannot be files the app owns, and they reset every colour the theme does not set.
  • Recent Kitty reloads its configuration by itself; on older versions the user presses Ctrl+Shift+F5.

Ghostty

  • The app creates ~/.config/ghostty/themes/velatura and adds one line, theme = velatura, to Ghostty's config (either of its two file names).
  • Detected and reported: an existing theme line (there is one here) and explicit colour keys, both of which override the theme.
  • The user reloads with Ctrl+Shift+Comma.

8. Icons, cursors, wallpaper, fonts

  • Selection of any installed icon theme, cursor theme, wallpaper or font is a plain settings change. The app sets both the light and the dark wallpaper keys. On Wayland some apps show a new cursor theme only after restarting.
  • Icon recolouring builds a per-user theme that inherits from the chosen base and contains recoloured copies of its coloured icons. Vector themes come first. Bitmap-only themes need pixel processing and are experimental; note that the icon theme in use on this machine is almost entirely bitmaps, so it falls in that later group. Monochrome symbolic icons already follow the text colour. Generated sets are for local use only, and are rebuilt from a recipe instead of being stored in backups.
  • Cursor recolouring edits cursor bitmaps and is experimental.

9. Other applications

Neovim (Phase 3)

Recommended method. The app creates a self-contained colourscheme, ~/.config/nvim/colors/velatura.lua, defining the standard highlight groups, common plugin groups and terminal colours, with no plugin dependency. The user activates it with colorscheme velatura in their own config; the app shows the line and never edits init.lua. For people who keep their own colourscheme, the app can instead write only a palette table for them to feed into it. Importing a theme from a running Neovim was proposed and is dropped for now, because it would mean running an external program against user configuration.

Starship (Phase 3)

Starship supports named palettes but has no include mechanism, so this is a key-level edit of starship.toml: add the [palettes.velatura] table and set palette, leaving everything else byte-identical. The prompt only changes where the user's format strings use the palette's colour names.

tmux (Phase 3)

A file the app creates, loaded by one source-file line. The user reloads the config.

Obsidian (Phase 3)

CSS snippets are a supported Obsidian feature. For each vault the user selects, the app writes .obsidian/snippets/velatura.css. The user enables the snippet in Obsidian's Appearance settings. Obsidian rewrites its own settings file while running, so the app does not edit it unless Obsidian is closed and the user opted in. Vaults are user data and often synchronised; nothing is written to a vault that was not explicitly chosen.

Firefox (Phase 4, experimental)

  • For each chosen profile: a stylesheet the app creates, one import line in chrome/userChrome.css placed according to CSS rules, and one line in user.js turning on the preference that makes Firefox load user stylesheets.
  • Mozilla does not support this mechanism and Firefox releases every four weeks, so it is the most fragile target.
  • Not fully reversible: once Firefox has read the preference it keeps it in its own settings; removing the line does not turn it off. Undo for this target ends with a step for the user.
  • Nothing is written while Firefox is running. Firefox must be restarted.

10. Not feasible or deferred

  • GDM login screen and lock screen.
  • Qt apps: deferred by decision.
  • Title bars of apps that draw their own (Kitty, Electron apps): GNOME does not draw title bars for Wayland apps.
  • Apps with hard-coded colours, and Electron or Chromium apps without their own theme mechanism.
  • Restyling of libadwaita apps beyond colour: not possible by design.
