Plan

Revision 2, rewritten after the five-perspective review. Approved by the owner on 2026-10-11. What changed from revision 1 is listed in Review findings.

1. Goal and scope

A GNOME desktop application, with a matching command-line tool, that applies one colour theme to the whole desktop from one place. It is meant for GNOME users in general, not only for this machine.

The app is a clean, independent project. The two existing palettes from ~/Workspace/Claude/system-theme (Aetherius and Ember) are imported as its first bundled themes. The old scripts are not reused and not modified.

In scope

  • Terminals: Kitty and Ghostty.
  • GTK4/libadwaita, GTK3, GNOME Shell, accent colour and dark/light style.
  • Flatpak apps; selection of icons, cursors, wallpaper and fonts among what is installed; recolouring of icons and cursors.
  • Neovim, Starship, tmux, Firefox, Obsidian.
  • A daytime and a night-time theme with manual switching and optional automatic switching.
  • A theme editor in the GUI.

Out of scope

  • Qt apps (deferred by decision), the GDM login screen and the lock screen (not reachable without root or unsupported Shell changes), Zen browser, Alacritty.
  • Anything that requires sudo. The app only detects system packages and tells the user how to install them.

2. Implementation options

The stated priorities are performance, security and size. The review corrected the first version of this comparison, which overstated Rust's advantages. The honest picture: the app's work is small file writes, so speed differences are modest except for icon recolouring; the design has no resident process in any language; and typed colour handling is a design choice available everywhere.

Recommendation. Rust for the engine and the CLI, decided now: compile-time guarantees on untrusted input, a single self-contained binary for timers and recovery from a text console, and icon throughput. The price is the larger supply chain and a slower start.

The owner chose Rust for the GUI as well. Phase 0 still measures binary size, crate count, start time, and recolouring speed against thresholds written down beforehand.

Build: Cargo alone must be able to build and test the engine and CLI; Meson wraps Cargo for the GUI, translations, desktop file and icons. UI files are written in Blueprint. Translations use gettext. The optional Shell extension is necessarily JavaScript.

3. Theme file format

One TOML file per theme. It holds colours and a few short names; it cannot contain commands, templates or paths. A theme has one or more named variants, each of which states whether it is light or dark. Which theme is used by day and which by night is the user's setting, not part of the file, and may pair two different themes.

schema = 1                 # file format version
derive = 1                 # version of the rule that fills in missing colours

[meta]
id          = "aetherius"  # lower-case slug [a-z0-9-]
name        = "Aetherius"
author      = "Rafa"
license     = "CC0-1.0"
description = "Starlit indigo with a periwinkle accent."

[variants.default]
name       = "Aetherius"
appearance = "dark"        # "dark" or "light"

[variants.default.palette] # open list of named colours: the lossless carrier for imports
sumi_ink_0   = "#0D101A"
sumi_ink_3   = "#141826"
sumi_ink_4   = "#1E2438"
fuji_white   = "#D3D9EE"
oni_violet   = "#8493D8"
winter_green = "#1D2B2A"
# ... as many as the theme has

[variants.default.ui]      # fixed roles; a value is a colour or a reference to the palette
bg           = "@sumi_ink_3"      # required
fg           = "@fuji_white"      # required
accent       = "@oni_violet"      # required
bg_dim       = "@sumi_ink_0"      # the rest are optional and derived when absent:
surface      = "@sumi_ink_4"      #   surface, border, fg_muted, fg_subtle, accent_fg,
                                  #   selection_bg, selection_fg, cursor, cursor_fg, link,
                                  #   success, warning, error

[variants.default.ansi]    # required: the 16 terminal colours
black = "@sumi_ink_0"
# ...

[variants.default.syntax]      # optional, about 16 roles for editors
keyword = "#A08CD0"            # may differ from the UI accent
[variants.default.diff]        # optional: add, change, delete, text
[variants.default.diagnostic]  # optional: error, warning, info, hint, ok

[variants.default.slots.starship]  # optional per-app adjustments; only slots that app declares
directory = "#7FA6DC"

[variants.default.suggests]    # optional and advisory: never applied unless the user accepts
icon_theme   = "Tela-purple"
cursor_theme = "capitaine-cursors"

Rules of the format:

  • Colours only. Values are #RRGGBB, or #RRGGBBAA where a role allows transparency, or a one-level @name reference into the same variant's palette.
  • No text from a theme file is ever written into a generated config, not even in a comment. Generated files carry only the theme's slug and a hash. Names and descriptions are shown in the app as plain text, with control and direction-override characters removed and lengths capped.
  • Suggestions are names, not paths. An icon or cursor suggestion is matched by exact name against what is installed. Wallpaper and fonts are not part of a theme at all; the user picks them from installed ones and the choice is stored with the user's settings.
  • Derivation is frozen per number. derive = 1 always produces the same colours; an improved rule becomes derive = 2. Bundled themes and themes saved by the editor write every role out explicitly.
  • Per-app slots are a declared list. Each target publishes its slot names (for Starship: directory, git, language and so on). Unknown slots or targets produce a warning, so a theme made for a newer version still loads.
  • Versioning. A file with a newer schema is refused with a clear message. Unknown keys load with a warning. The editor preserves comments and unknown keys when saving. A user's file is never rewritten in place by an upgrade.
  • Limits. Size cap before parsing; reserved ids for bundled themes; an imported theme whose id already exists must be renamed or explicitly replace the other.
  • User themes live in ~/.local/share/velatura/themes/. Bundled themes are read-only and are duplicated before editing.

The first version of this format could not hold Aetherius and Ember without loss (they have 44 named colours each). The open palette table and the diff and diagnostic groups fix that. Importers for base16/base24 and Kitty themes come later and produce this same format.

4. Safety requirements

These are requirements on the engine. The mechanics are in Architecture.

  1. User level only. No sudo, no polkit. Each target may write only to its own fixed directories, checked after resolving symlinks.
  2. Back up before every change. The pre-change state of every file and setting is recorded before it is touched. The first time the app ever touches an item, that state is added to a permanent "original setup" record.
  3. Preview is the plan that gets applied. The preview produces a plan object; apply executes that same object and refuses to run if any file changed in between.
  4. Undo and restore. Undo reverses the last change the user made. Any backup can be restored. The original setup is never pruned. Twenty backups are kept by default.
  5. The user's own content is never lost. In a file the user maintains, the app changes only the span it added. Undo removes that span from the file as it is now, so edits made since are kept.
  6. Never delete existing configuration. Files the user wrote are never removed. The one exception, which needs approval, is directories the app generated itself and can regenerate (icon sets, Shell theme folders).
  7. All-or-nothing for files; best effort for settings. File changes are atomic and rolled back together on failure. GNOME settings cannot be made fully transactional; they are written last, in one batch, and restored on failure.
  8. Crash recovery never overwrites newer work. After an interrupted apply, a file is rolled back only if it still contains exactly what the interrupted apply wrote.
  9. The app does not restart, reload or signal other programs. After an apply it lists exactly what the user needs to do, with copyable instructions.
  10. Unattended runs never ask and never cross a consent boundary. A scheduled switch skips anything that would need a decision, applies the rest, and records what was skipped for the user to see later.
  11. An unreadable theme cannot lock the user out. Themes below a contrast floor need explicit confirmation and auto-revert unless confirmed; the app's own window stays readable under any theme; and recovery works from a text console.
  12. Coexistence is checked, not assumed. The app detects other tools that rewrite the same files, and existing settings that would silently override the theme, and reports both before applying.
  13. Theme files are untrusted input. See section 3.

5. Daytime and night-time themes

  • The user's settings name a daytime theme and a night-time theme. They can be two themes or two variants of one. The labels "day" and "night" are used only for scheduling; they are never used to mean light and dark.
  • Manual: a control in the GUI and velatura switch day|night|toggle.
  • Scheduled: one systemd user timer runs velatura switch auto, which works out the right theme for the current time, so a missed trigger (suspend, late login) corrects itself. No process stays resident. Scheduling is only offered once the CLI is installed at a stable path.
  • Follow the GNOME dark style: offered only for a light and dark pair. In this mode the app does not set the dark style itself, to avoid a feedback loop.
  • Limitation, stated before enabling: a switch recolours the top bar, terminals and newly opened apps; GTK apps that are already open keep the old colours until restarted.

8. Definition of done for the MVP

The MVP (phases 1a to 1d) is done when all of the following hold on GNOME 50 and 51, upstream session, Wayland. The code is built against the libadwaita 1.6 interface so that older versions can be added afterwards as tested data.

Behaviour

  1. Applying a bundled theme leaves the files and settings of Kitty, Ghostty, GTK4/libadwaita, GTK3 (when adw-gtk3 is present), GNOME Shell (when User Themes is active), accent and dark style in the expected state, and an automated probe confirms that GTK and the Shell compute the expected colours.
  2. Targets that are not installed, or that are missing a prerequisite, are skipped with a reason and do not fail the apply.
  3. Where an existing setting would override the theme, the target is reported as "set up but not taking effect", with the reason. It is never reported as applied.
  4. Switching between the daytime and night-time themes works from the GUI and the CLI.

Safety

  1. Preview lists every file and setting that will change and changes nothing. Apply refuses a plan whose files changed since the preview.
  2. After Undo, every file the app touched has its previous content, permissions and security label, provided nothing else changed it meanwhile, and every setting the app wrote is back to its previous value or unset state. Content the user added outside the app's span is preserved. Known exceptions are documented per target.
  3. "Restore original setup" returns every item the app has ever touched to its recorded first state, reporting any item that conflicts.
  4. After recovery from an apply interrupted at any step, the state equals the state before that apply, and no file edited since is overwritten.
  5. No content outside the app's own files and spans is changed; nothing is written outside the per-target directories; nothing runs with elevated rights.
  6. The hostile-theme tests pass for every target.
  7. Recovery from a text console works without the GUI and without a session bus (files restored, unrestored settings listed with the exact commands).
  8. Other theming tools and timers touching the same files are detected and reported before the first apply.

Experience

  1. A first-time user applies a bundled theme in four interactions or fewer, with no terminal and no detours.
  2. The theme in use is always visible, and Undo is always reachable from the menu, not only from a transient message.
  3. The app's own window stays readable under any applied theme. A theme below the contrast floor cannot be applied without explicit confirmation. With High Contrast on, GTK and Shell recolouring is skipped and the user is told.
  4. After applying, the app states what took effect now and what the user must reload or restart, and does none of it itself.
  5. Each failure class (not applied, skipped, conflict, busy, rollback incomplete) has a designed, translated message.
  6. All user-visible text is translatable. The manual checklist of section 6 passes.
  7. One-step "Remove all of Velatura's changes" exists in the GUI and CLI.
  8. The automated test layers pass in CI and the documentation in docs/ matches what was built.
