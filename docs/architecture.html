Architecture

Revision 2, rewritten after the review. How the code is organised, how an apply works, how the GUI is laid out, and how distribution is kept open.

1. Components

│   ├── velatura-engine/   plans, connectors, transactions, backups, host-access layer

Bundled themes and all version-specific data are compiled into the binaries, so they are found the same way when running from source, from a user-prefix install, from a package or from a sandbox. Messages, hints and errors cross the engine boundary as typed values with a stable code and arguments; the CLI and GUI turn them into translated text.

Dependency budget for the theme and engine crates: TOML reading and comment-preserving editing, JSON, error and logging facades, a hash, safe temporary files, a diff library, and GIO behind a feature switch. Colour maths, contrast, marker editing, key-file editing and placeholder substitution are written in-house. No regular-expression engine, async runtime, template engine or date library. CI fails if the crate count per binary exceeds a stated cap.

2. Data model

  • Theme and Variant: parsed and validated TOML.
  • ResolvedTheme: sanitised identity, appearance, every role as a typed Color, and per-target slot values. A Color can only be formatted through a closed set of functions.
  • Instance: one concrete thing to theme, identified by target and instance, for example kitty:default, firefox:default-release, obsidian:<vault id>. Preferences, consent, backups, status and --only are all keyed this way.
  • Facts: what probing found about an instance: paths, versions, prerequisites, conflicts. Serialisable, so plans can be tested from stored facts.
  • Plan: an ordered list of Changes, each with the precondition it was computed against, plus conflicts needing an answer and hints for afterwards. Serialisable.

3. Targets: renderer and connector

The first design claimed targets could be pure planners. The review showed that is false for most of them (Kitty must read kitty.conf, Firefox must find profiles). Each target is now two parts with a read-only probing step between them.

trait Renderer {                       // colours -> bytes. Pure, golden-tested.
    fn render(&self, theme: &ResolvedTheme, opts: &RenderOpts) -> Artifacts;
}

trait Connector {                      // where the bytes go
    fn id(&self) -> TargetId;
    fn requires(&self) -> &[HostCapability];           // e.g. Systemd, ShellDbus, HostExec
    fn probe(&self, host: &dyn HostRead) -> Probe;      // read-only: instances + facts
    fn plan(&self, art: &Artifacts, facts: &Facts, prefs: &InstancePrefs)
        -> Result<TargetPlan, PlanError>;               // pure
}

enum Change {
    WriteOwnedFile  { path, content, mode },
    RemoveOwned     { path },                    // moved into the backup store, not unlinked
    CreateDir       { path, mode },              // undone only if still empty and created by us
    Symlink         { path, target },            // e.g. timer enablement links
    ManagedBlock    { path, marker, content, placement, comment_style },
    StructuredEdit  { path, format, edits },     // key-level and list-member-level edits
    SetSetting      { schema, schema_source, path, key, value },
    InstallTree     { dest, staged, recipe_hash } // generated icon sets, by directory rename
}
  • Nothing happens that is not a Change. Creating a directory, enabling a timer or granting a Flatpak permission are all Changes, so they appear in the preview and in the backup. The Flatpak override is an edit of Flatpak's own key file, not a call to the flatpak program.
  • Simple renderers are embedded template files filled by an in-house substitution of the form {role|format} with four formats and no conditionals or loops. One named-colour renderer serves GTK4, GTK3 and Flatpak; one CSS-variable renderer serves Obsidian and Firefox. Third-party templates are a later, separate decision.
  • Version-specific data is a single list per target annotated with "since" and "removed", split only when a release makes a name harmful.

4. Host-access layer

All contact with the machine goes through one layer, defined in Phase 0 and enforced by a lint that bans direct file, process and directory-lookup calls elsewhere. It has a real implementation, a failure-injecting wrapper for tests, and room for a sandboxed implementation later.

PartCovers
DirectoriesThe host's XDG directories (never the process's own, which differ in a sandbox), system data directories taken from XDG_DATA_DIRS.
FilesRead, atomic write, rename, create and remove empty directory, canonicalise, sync, free space; each path classified as visible, not reachable or portal-backed.
SettingsGIO settings: user value versus default, set, reset, writability, schemas from the default source or from an extension's own directory. Asserts at start that the real dconf backend is in use.
Session busGNOME Shell's extension interface: Shell version, list, install request, enable request.
ProgramsA closed list. After the review it contains only systemctl --user. Version probing of apps is optional and falls back to conservative behaviour.
SelfHow to invoke this CLI from a timer, and which install channel is running.
ClockFor schedules and tests.

5. Apply engine

  1. Lock. An operating-system file lock in the state directory. A second caller waits up to five seconds, then returns "busy" with its own exit code.
  2. Recover. If the journal shows an unfinished apply, examine each item: unchanged from before is left alone; equal to what the interrupted apply wrote is rolled back; anything else was edited since and is kept and reported.
  3. Probe and plan. Each enabled connector probes its instances and returns Changes, conflicts and hints.
  4. Check. Resolve symlinks on both the path and the home directory. Confirm the real location is in that target's allow-list and is the expected kind of file. Try creating a temporary file in the destination directory. Check that settings keys exist and are writable. Note whether the owning app is running, whether an editor has the file open, and whether the file is hard-linked.
    • A failed precondition demotes that instance to "skipped, with reason". It never aborts the others.
    • Drift is measured only on what the app owns: the whole of an owned file, the bytes between markers, or the named keys.
    • Shadowing analysis: would something already in the user's configuration override the theme? If so the instance is marked "set up but not taking effect".
  5. Preview stops here and returns the plan.
  6. Resolve. The caller supplies answers to conflicts. Interactive callers ask the user. Unattended callers use a fixed policy: skip, record, continue.
  7. Back up. Store pre-change content, sync it, then write the manifest by rename. The manifest is the commit marker; a backup without a valid manifest is ignored.
  8. Execute. Journal the start. For each file: re-verify its precondition immediately before writing and abort as "stale" on mismatch; write a temporary file in the same directory, copy extended attributes, access lists and security label, sync, rename, sync the directory. Symlinked files are written through to the real file. Generated trees are installed by directory rename. Every fallible step is done before settings, which are written last in a single batch and synced.
  9. Verify, then commit or roll back. Rollback restores by copying, never by moving, so security labels stay correct.
  10. Report what changed, what was skipped and why, and the hints.

Backups

  • Store: ~/.local/share/velatura/backups/, content-addressed, owner-only, marked as a cache directory for backup tools to skip. Blobs are verified on read; pruning runs under the lock and never removes anything referenced by the original-setup ledger or an unfinished apply.
  • Original setup: an append-only ledger. The first time any path or setting is touched, its state is added. It is labelled "state before Velatura" with its date, because on a machine that was already themed it is not a pristine state.
  • Undo is the inverse operation, not a file copy. For a managed block: remove or replace the block in the file as it is now. For a structured edit: put the keys or list members back. For a setting: restore only if the current value is still the one the app wrote; otherwise report a conflict. The stored full copy is the last resort.
  • Generated trees are recorded as a recipe and a hash, not as content.
  • Retention: the ledger for ever; 20 user-initiated backups; three slots for scheduled switches. Undo targets the last user-initiated change.
  • Formats are versioned. Every persisted file carries a version; a newer version makes the app read-only; a test restores a first-version backup on every future build.
  • Recoverable by hand. Manifests are JSON and the store is plain files. An emergency card (first run, --help, docs) gives the exact commands for a text console.

File ownership rules

KindRule
Owned fileOwned only if the state record lists it and its hash matches. A file that merely has the app's name is treated as the user's. Header contains the slug and a hash, nothing from the theme.
Managed blockExactly one well-formed pair of single-line markers carrying the target id and a format version. Anything else (one marker, duplicates, nesting) means refuse and report. Edited as bytes, keeping the file's line endings, encoding and final-newline state. Placement follows each format's rules.
Structured editFor formats with no place for a marker (JSON, key files). The prior state of each key or list member is recorded, so removal takes out only what the app added. After editing, the untouched parts are compared and the edit is refused if they differ.
"Show me the line"For every managed block the user can decline the edit and add the line themselves. This is the recommended path for files managed by a dotfile tool; the app detects stow, chezmoi, yadm and home-manager and says where bytes would really land.

Security boundaries

  • Theme files are hostile until proven otherwise: schema, size cap, typed colours, numeric ranges, reserved ids.
  • No theme string reaches a generated file. References are matched by equality against enumerated installed items, never joined into a path.
  • Names shown in the GUI are plain text with markup disabled; CLI output is stripped of control sequences.
  • Diagnostic reports redact the home directory, profile names and vault names by default.
  • No network access in the engine. Installing User Themes is delegated to GNOME Shell's own installer and dialog.

6. Where things are stored

PathContent
~/.config/velatura/config.tomlPortable preferences only: schedule, retention, day and night choice.
~/.local/state/velatura/Machine facts: consents, selected instances, accepted suggestions, what is applied, last-written hashes, lock, journal, results of unattended runs, the install channel.
~/.local/share/velatura/themes/User themes.
~/.local/share/velatura/backups/Backups and the original-setup ledger.
~/.cache/velatura/Staged icon sets; safe to delete.

Consents are kept out of ~/.config because people synchronise that directory between machines. These locations are the same in every install channel; a second install of a different channel finds the first one's state and refuses to manage the same files until told to import it.

7. Command line

Built so far (Phase 1a): list, show, validate, targets, status, apply, undo, history, restore, recover, doctor. Exit codes: 0 done, 1 failed, 2 wrong usage, 3 agreement needed and nothing changed, 4 another Velatura is running, 5 done but something was left out. The rest of the list below arrives with later phases.
velatura                               status and short help
velatura list | show <theme> | validate <file> [--strict]
velatura targets                       apps and desktop parts: instances, support, prerequisites
velatura status                        theme in use, per-instance state, things left for you to do
velatura apply <theme>[/variant] [--only ..] [--except ..] [--preview] [--yes] [--if-stale]
velatura switch day|night|toggle|auto
velatura undo                          (alias: revert)
velatura history [verify]
velatura restore <id> | --original [--preview]
velatura disconnect <target> | --all   remove what the app added
velatura doctor                        versions, prerequisites, conflicts, other theming tools
velatura schedule set --day 07:00 --night 20:00 | off | status
velatura theme import|export|resolve
  • Words match the GUI: Undo, History, Preview. One glossary is shared by GUI, CLI and docs.
  • The first apply that adds a line to a user's file needs confirmation on a terminal or --yes. Without a terminal and without --yes it changes nothing and exits with the conflict code.
  • --json on every command, with a format number, stable codes and a documented exit-code table. Human output is translated; command names, JSON keys and exit codes are not.

8. GUI structure

A libadwaita application built only on the 1.6 interface. Widgets that need newer versions are not used. It follows the GNOME Human Interface Guidelines; Interface guidelines holds the rules and lists where they correct this section (H1 to H8).

Screens

  • Themes. A list of themes with swatches, each tagged Dark or Light in text. The theme in use carries a check mark and "In use". A theme page shows the preview and one primary button, "Apply Theme", which reads "Applied" when nothing would change.
  • Preview. The window part is built from real libadwaita widgets with locally scoped colours, so it shows what GTK will actually do. The top bar and terminal are drawings, captioned as illustrations. One line underneath: "Some apps keep their own colours."
  • Apply flow: four steps. Pick; press Apply Theme; one confirmation in plain words ("Adds one line to your Kitty settings. Creates 4 files. Changes 3 system settings. Nothing is deleted. You can undo this at any time."), with details and diffs behind an expander; then a result page in the same dialog: what changed now, what changes when apps are reopened, the exact steps left to the user with a copy button, and Undo.
  • Apps & Desktop. One system-wide page with a row per app: status, set-up action, a switch meaning "include when applying themes", and Stop Theming. Turning a switch off asks whether to keep the current colours or remove them. Optional items (User Themes, adw-gtk3) appear here as set-up rows and never block an apply.
  • History. Backups with date, theme and cause; Restore; Restore Original Setup; store size.
  • Editor (Phase 2). Three colours first (background, text, accent) with everything else derived and shown; expanders for Interface, Terminal and Code; each derived colour can be made custom and reset to automatic; contrast problems in plain words with a Fix button; Save and Discard; bundled themes offer Duplicate to Edit.
  • Import (Phase 2). Shows a preview, name and author as plain text, and the statement that theme files contain only colours and names and cannot run anything.
  • Preferences, Troubleshooting, About, Shortcuts, empty states, and a "scheduled switch in progress" state.

Rules

  • The app must stay readable under any theme. Its own window uses stock colours regardless of the user's gtk.css. How to do this reliably is a Phase 0 spike; if it cannot be done, the console recovery path is the documented fallback.
  • Undo is persistent: on the result page and in the primary menu, not only in a transient message.
  • Contrast guard. Below 4.5 to 1 for text on background, Apply needs "Apply Anyway", which is never the default, and then shows a "Keep this theme?" countdown that reverts unless confirmed.
  • High Contrast. When the system setting is on, GTK and Shell recolouring is skipped with an explanation; Troubleshooting flags a theme that is overriding colours while High Contrast is on.
  • Outside changes. If the dark style or accent is changed elsewhere after an apply, the app shows it and offers to reapply; it does not silently change it back.
  • Failures have three designed forms: nothing was changed (with reason); some apps skipped (a line on the result page); rollback incomplete (each affected file and its backup location, plus the console command).
  • Conflict prompt: "You changed Kitty's theme file since last time", with Keep My Changes as the default, Replace, and Show Changes.
  • Accessibility: labelled swatches, status never by colour alone, diffs marked with plus and minus, layouts that hold at 360 px and at 200% text, no animation when animations are off.
  • Translation: named placeholders, plural forms, locale date formats; role names such as "Sidebar background" are translatable; a pseudo-locale and a right-to-left run are part of the MVP checklist.

9. Version support

  • MVP verified on GNOME 50 and 51, upstream session. GNOME 47–49 and the Ubuntu session follow in Phase 2 as tested data; Ubuntu ships a modified Shell stylesheet and is unsupported until tested.
  • The GUI is compiled against the libadwaita 1.6 and GTK 4.16 interfaces only.
  • Flatpak apps use the GTK of their runtime, not the host's, so generated GTK stylesheets must be valid for every runtime in use, not just the host version.
  • On a GNOME version that has not been tested, the Shell target is off by default with an explanation.
  • Generated Shell themes are stamped with the Shell version they were made for. Because they are overrides only, a stale one degrades to "some colours not applied" instead of a broken Shell; apply --if-stale regenerates it.

10. Distribution

Run from source for now. The recommended order afterwards:

  1. User-prefix install from source (~/.local), which also works on immutable systems and gives the CLI a stable path for timers.
  2. COPR, AUR and a tarball with vendored crates. Fedora 44 already packages the needed Rust GTK crates, so an official Fedora package is possible later.
  3. The Shell extension on extensions.gnome.org, versioned separately, with a fixed identifier and a one-file contract with the app.
  4. A self-hosted Flatpak repository with full permissions, mainly for immutable desktops.
  5. Flathub: only as a reduced edition, if at all. The full app needs about a dozen permission exceptions (home configuration directories, host system data, host settings, user timers, host commands), and Flathub does not accept system utilities that mainly act on the host. Flathub also requires disclosure of AI-generated material, forbids AI-generated or AI-assisted content in the submission manifest, and refuses sandbox-escaping exceptions where it sees signs of LLM use. Since this project is being developed with AI assistance, that policy applies and the owner should read it before planning on Flathub.

Each connector declares which host capabilities it needs, so a restricted build can switch a target off with an explanation instead of failing. Fixed in Phase 0 because they are expensive to change later: application ID, CLI and GUI binary names, gettext domain, extension identifier, timer unit names.
