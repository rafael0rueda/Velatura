Phase 3c – Ptyxis and GNOME Text Editor

Branch phase-3c-gnome-apps. Completed 2026-10-13. The third of four slices of Phase 3 (D54). Both were candidates "to verify" (D34); both turned out to have a supported way in, and both pass the same transaction tests as the other targets, which is the slice's exit condition.

On the owner's desktop nothing was changed. Both apps are installed there and were read, not written: their settings were listed, and files that come inside the two programs were looked at. Everything else ran in throw-away home folders with a private settings store.

What verifying them showed

QuestionResult
Can Ptyxis take a palette that is not one of its own?Yes: it reads palette files from ~/.local/share/org.gnome.Ptyxis/palettes/, and each profile has a palette setting that names one by its file name. Supported, and offered in its preferences.
Where are a profile's settings?At a path made of the profile's id, /org/gnome/Ptyxis/Profiles/<id>/, not at a fixed place. Velatura's settings layer could not read such a setting; it can now.
What does a palette hold?A light and a dark set, each with text, background, cursor and the sixteen terminal colours. Every set of the 244 palettes inside Ptyxis 50.1 has exactly those keys; a few add title bar colours. Most palettes have one set only.
Can Ptyxis check a palette for us?No. Its --import-palette copies any file in, a line of nonsense included, and says nothing. The gate therefore compares the generated file with a palette taken from inside the installed Ptyxis.
How does Text Editor choose its colours for code?A GtkSourceView style scheme, named by its setting style-scheme. GtkSourceView reads the user's own schemes from ~/.local/share/gtksourceview-5/styles/. Supported; the same folder serves every app that shows code with GtkSourceView 5.
Can GtkSourceView check a scheme for us?Yes, from Python and without a window. The gate has it load each generated scheme and give back every style with the file's colours; a file with one wrong word is refused.

Added

  • Ptyxis. A palette of Velatura's own, velatura.palette, among the user's palettes, and the default profile set to use it. Both of the palette's sets hold the theme's colours, so the terminal shows the theme whichever style Ptyxis is in. The profile's earlier palette is recorded and comes back with Undo.
  • GNOME Text Editor. A style scheme of Velatura's own, velatura.xml, with sixty styles: the view (text, selection, cursor, current line, line numbers, search), the styles languages build on, text with markup, and a few languages by name. The editor's style-scheme is set to it; the earlier one comes back with Undo. The scheme says whether it is light or dark.
  • Both ask the first time. Neither adds a line to a file of the user's, but each changes how an app looks. The first change to each is made only when agreed to, so a scheduled switch never starts theming one of them by itself. After that they follow every switch.
  • Settings at a path. The settings layer reads and writes a schema placed at a given path (id:/path/, the form gsettings takes), refusing a path that is not well formed. A profile id that could not be part of such a path is never used to build one.
  • In the app, Ptyxis under Terminals and Text Editor under Apps, each with its switch. In the command, ptyxis and texteditor for --only and --except.
  • What is reported. That only the default profile was given the palette, when Ptyxis has several or none yet; that open Ptyxis windows may need reopening; that Text Editor shows the scheme once reopened; a setting an administrator has locked.

Tests and checks

  • Five transaction tests in tests/gnome_apps.rs: apply, apply again (no setting written), another theme, and two undos back to the exact start; a crash at every step, from a clean home and an applied one; a palette or style the user chose before comes back with Undo, and one chosen since is kept; only the default profile is set; apps that are not installed, a locked setting, and a file of that name that is not Velatura's.
  • One test through the command against a real, private settings store: a profile's setting at its path is set and put back, which only the real store can show.
  • Golden files for both generated texts of each bundled theme, and a test that no style is set twice.
  • In the gate: GtkSourceView loads each scheme and returns all sixty styles with their colours; the palette is compared with one from inside the installed Ptyxis. Both apps are added to the CI image.
  • 170 tests in all. The translation template has 377 strings, all in Spanish.

Changed from the plan

  • Both candidates are in, as official mechanisms. The plan had them as "to verify".
  • The choices made on the way are in D57, proposed: the default profile only; agreement before the first change; one palette whose two sets are the same; schemes and palettes under one fixed name.

Not done, and what only a person can do

  • Neither app was looked at with the theme in it. Ptyxis cannot be asked what it shows. Whether a running Ptyxis picks up a rewritten palette at once, and whether Text Editor does so for a rewritten scheme, was not observed; the result says to reopen them if they keep the old colours. This needs a person at a real session.
  • Applying the two on the owner's desktop was not done: it needs the owner's go-ahead. The owner's default profile uses the palette dracula and Text Editor the scheme kate-dark today; both would be recorded and come back with Undo.
  • Ptyxis and Text Editor installed as Flatpak apps keep their files and settings elsewhere and are not reached.
  • Other Ptyxis profiles are left as they are. The palette is there to choose for them.
  • Text Editor's own light or dark look (style-variant) is not changed. It follows the desktop's style, which the theme sets.
  • Other apps with GtkSourceView 5 (Builder among them) find the scheme in their lists, and are not set to it.
  • Title bar colours in the Ptyxis palette are not set; Ptyxis works them out from the background.
