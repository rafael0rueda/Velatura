Phase 2d – Velatura's Shell extension, and following the dark style

Branch phase-2d-extension. Completed 2026-10-13. The fourth slice of Phase 2 (D47). Its exit condition in the roadmap: the Shell shows the theme where other extensions' stylesheets win today. It does, in a real GNOME Shell 50 started by the gate.

On the owner's desktop nothing was changed. The extension was not installed in the real session, and no systemd unit was written. Everything ran in throw-away sessions.

Added

  • Velatura's own Shell extension, in extension/: about fifty lines that load one stylesheet, ~/.local/share/velatura/shell/gnome-shell.css, and load it again when that file changes. It holds no colours and no settings, starts no programs and patches nothing in the Shell, so it is the same for every theme and never needs updating for one.
  • Installing it. velatura extension install, or Install in the new Shell Extension group on the Apps & Desktop page, puts the two files in the user's extensions folder. velatura extension says where it stands; extension remove takes Velatura's copy away. Velatura does not turn it on (D44): it says that the Shell sees a new extension after signing out and in, and where to turn it on.
  • The Shell target uses it when it is on. The top bar and overview then get one stylesheet in one place, replaced in place: no folder per theme and no setting to flip. What was made for User Themes is cleared in the same apply, and the other way round if the extension is turned off again. Undo walks back through either move.
  • It wins where User Themes loses. Between two rules of the same weight the Shell does not go by which stylesheet was loaded last, so for the extension every selector's first part is written twice (#panel#panel). That is one step heavier than the plain #panel an extension typically uses, and still lighter than a rule written on purpose for a narrower case, which keeps winning.
  • Following the dark style. velatura schedule follow, or Follow the Dark Style on the Themes page, changes to the nighttime theme when the desktop goes to its dark style and to the daytime theme when it goes back. It needs a light theme for the day and a dark one for the night, and replaces the clock: one or the other is on. While it is on, applying a theme leaves the style setting alone, so the two cannot chase each other.
  • A packing script, scripts/pack-extension.sh, makes the zip that extensions.gnome.org takes.

How following works

There is still no process that stays running. A systemd path unit watches the file the desktop keeps its settings in and starts velatura switch auto when it changes. That file changes with any setting, so the command is started often; it compares the style with the one it last saw to and does nothing unless they differ. A theme picked by hand therefore stays until the style changes again.

Tried on a real session

On 2026-10-13, with the owner's go-ahead, the trigger was tried on the owner's session with two throw-away units that only logged, not with Velatura's own. The style was changed four times and forty unrelated settings were written in a row. Afterwards the units were removed and the style put back; nothing else was touched.

QuestionResult
Does a change of style start the service?Yes, every time, within the same second.
Forty writes in a row, with systemd's default limitAfter four starts systemd refused the fifth ("start request repeated too quickly"), the watching unit failed, and a later change of style was missed. This was a defect in the first version of this slice.
The same with the limit lifted (StartLimitIntervalSec=0)Nineteen starts for the forty writes, the unit stayed active, and the change of style after the burst was noticed. The service is now written this way, and a test holds it.

Not tried: Velatura's own units through a sign-out and sign-in, and the cost of the starts over a working day.

Tests and checks

  • In a real GNOME Shell 50, in the gate: another extension colours the panel; with User Themes the theme loses to it; with Velatura's extension on, the panel shows Ember, then Aetherius after the file is replaced while the Shell runs, then the other extension's colours again after undo. Seven checks in all, with no error from the extension in the Shell's log.
  • Seven engine tests: install, update and remove without a trace, and a folder of that name that is not Velatura's left alone; apply and undo through the extension; moving between User Themes and the extension in both directions; the exhaustive crash test; following refused without a light and dark pair; the theme following the style and never setting it.
  • The published files are checked for what they must not contain: nothing that starts a program, reaches the network or reads settings, and everything connected in enable() undone in disable().
  • The command end to end, and the rules for the extension rendered and compared with the User Themes ones.
  • 132 tests in all. The translation template has 334 strings.

Not done, and what only the owner can do

  • Publishing on extensions.gnome.org. It needs the owner's account there, and a review by GNOME's reviewers. The zip is ready. Until it is published the extension is installed from the app, which means signing out and in once.
  • Following the dark style has not been turned on for real. The trigger was confirmed on a real session with throw-away units (above); Velatura's own units have not been enabled there. Every change of any setting starts the command, which leaves two lines in the journal each time.
  • A real GNOME Shell 51: the Shell check runs on 50, the version installed here.
  • Extensions with heavier rules still win where those rules apply, by design.
  • The lock screen keeps the stock look: extensions are not active there.
