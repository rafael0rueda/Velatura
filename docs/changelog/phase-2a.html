Phase 2a – switching on a schedule

Branch phase-2a-schedule. Completed 2026-10-12. The first slice of Phase 2, which is built in slices like Phase 1 was (D47). The roadmap's exit condition for Phase 2 has two halves; this slice delivers the second, "switches on schedule without the GUI running".

On the owner's desktop nothing was changed. The schedule was built and tested in throw-away home folders with a stand-in for systemctl. It has not been turned on here, and no timer was written to the real session.

Added

  • A schedule. velatura schedule set --day 07:00 --night 20:00, or the new Schedule group on the Themes page, writes one systemd user timer and its service into ~/.config/systemd/user and turns the timer on with systemctl --user. velatura schedule off turns it off and removes both files. velatura schedule shows the state. The two files hold the path of the command and the two times, and nothing else.
  • velatura switch auto, which the timer runs. It works out which of the two themes belongs to the present time and applies it. It acts once per part of the day: a theme picked by hand in the afternoon stays until the evening. A start missed while the machine was off or asleep is made up for at the next one, because the timer is persistent and the command compares against the last part of the day it saw to.
  • The rules for a run with no one present, from the plan's safety requirements: nothing is asked; a file of the user's that was never agreed to is not touched; nothing is removed, not even a folder Velatura generated itself (D29); and what was left out is recorded. The record is shown by velatura status, by velatura schedule and as a banner in the app, and is cleared by the next apply the user makes.
  • One backup for the schedule. A scheduled switch on top of a scheduled switch is merged into the same backup, so weeks of switching take one place in History between two changes of the user's, and never push those out. Two switches that cancel each other leave no backup at all.
  • Undo goes past the schedule. Undo reverses the last change the user made, together with whatever the schedule switched after it, in one step.
  • Removing everything removes the timer too, in the app and in velatura restore --original.

Refused, with a reason

CaseWhat happens
No daytime or no nighttime theme chosenThe schedule is not turned on. The switch in the app is insensitive and says so.
The command runs from a build folderNot turned on: the next build or clean would take the command away from under the timer. The schedule needs the copy in ~/.local/bin or a packaged one.
Another timer with "theme" in its name is enabledNot turned on, and the timer is named. --yes, or Turn On in the app's question, turns it on all the same.
A file with the timer's name exists and Velatura did not write itNot turned on; the file is left as it is.
systemd does not take the timerThe two files are removed again and the schedule stays off.
A timer file was edited by handReported as damaged. Turning the schedule off leaves that file in place and says so.

Tests and checks

  • Twelve engine tests for the schedule, among them: the switch stopped at every step on top of an earlier scheduled switch, then recovered, with the state and the shared backup as before and Undo still reaching the start; edits made by the user between two scheduled switches surviving Undo; and scheduled backups not counting towards the twenty kept.
  • systemd-analyze verify accepts the generated unit files (run where it is installed).
  • The command end to end in a private session: set up from an installed copy, run as the timer runs it, undone, and removed, with a stand-in systemctl that records its orders.
  • The gate renders the app with a schedule on and checks that the window shows it and says what the last switch left out.
  • 97 tests in all. The translation template has 202 strings.

Changed from the plan

  • The timer is set up outside the undo history (D48). The architecture had every action as a change in a plan, with a backup. Undo is for changes of theme; if turning the schedule on were a step in that history, Undo Last Apply would sometimes turn the schedule off instead. Turning it off is its own reverse, and it is checked the same way: only files Velatura wrote, identified by their content, are ever replaced or removed.
  • One merged backup instead of three slots for scheduled switches (D48). Dropping the oldest of several scheduled backups would leave a gap in the chain that Undo walks.
  • systemctl creates the link that enables the timer; Velatura does not write it itself.

Not done in this slice

  • Following the GNOME dark style. It needs a light and a dark theme as a pair, and both bundled themes are dark, so it could not be used or checked yet. It also needs a trigger without a resident process; the candidate is a systemd path unit on the settings database, which can only be confirmed on a real session. Moved to the slice with the companion extension (D49).
  • A notification after a scheduled switch that needed attention (D32, proposed, off by default). The same information is in the app's banner and in status.
  • A real systemd user session. The timer has not fired on a real machine: that is a change to a live session and waits for the owner's go-ahead. What systemd does with the files is covered only by systemd-analyze verify.
  • The times are typed as 24-hour HH:MM, in the app too.
