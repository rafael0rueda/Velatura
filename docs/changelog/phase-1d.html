Phase 1d – GNOME Shell and the day/night switch

Branch phase-1d-shell. Completed 2026-10-12. Exit condition from the roadmap: the MVP's definition of done. It is not fully met: 12 of its 20 lines are met, 7 partly and 1 not. The table below says which and why.

On the owner's desktop nothing new was applied. The Shell target was run in a headless GNOME Shell inside a throw-away session, and previewed read-only on the real one.

Added

  • Top bar, overview, menus and dialogs through the User Themes extension. The generated theme is a folder with one stylesheet of colour overrides for 17 selectors, layered over the Shell's own. It never copies the stock stylesheet.
  • A new folder name per theme, Velatura-<colours>-<format>, because the Shell reloads only when the name changes. The folder of the previous theme is removed in the same step and comes back with undo.
  • User Themes installed for one user keeps its setting in its own folder; that is now looked up there.
  • What hides the theme is reported: User Themes being turned off, and every enabled extension that ships its own stylesheet, since those always win.
  • Day and night. A daytime and a nighttime theme are chosen once, in the app (Themes, Day and Night) or with velatura switch set day <theme>; then one button, or velatura switch day, night or toggle, changes between them. The choice is kept in ~/.config/velatura/config.toml, which a person can read and edit.
  • "Set up, but not taking effect" as a state in Apps & Desktop, with the reason.
  • Recovery from a text console: without a desktop session the files are put back and each setting that could not be is listed with the command to run later.

Fixed

  • A change reported as done that had not happened. Run without a desktop session, the settings store accepts a write and drops it. Since Phase 1a the command then said it had changed the setting. Now such a store counts as unavailable, and every setting written is read back before the change is recorded; a setting that did not take its value fails the operation and rolls it back.

Tests and checks

  • In a real GNOME Shell 50.5, headless, in every local gate run: the command applies Ember before the Shell starts and the panel shows Ember's colours; Aetherius is applied while it runs and the panel changes; both are undone and the panel is back to stock.
  • A libadwaita app computes all 58 opaque colours of each generated stylesheet, over conflicting definitions earlier in the same file. Local gate, needs a display.
  • Every selector used exists in the stock stylesheet of GNOME Shell 50 (1,958 selectors stored as a fixture); the shape of every generated rule is checked, because one syntax error makes the Shell drop the whole file.
  • Transaction tests for the Shell target, and the exhaustive crash test now runs over all six targets. 84 tests.

Changed from the plan

  • Velatura does not turn User Themes on itself (D44). It writes the theme and the name, and says that the extension is off and where to turn it on. The plan had it ask the Shell to enable the extension.
  • The accent is still the system's. As planned, the Shell shows the nearest of GNOME's nine accents, not the theme's exact one.

Not done in this phase

  • GNOME 51 and GNOME 47 to 49: selector fixtures and Shell runs exist for 50 only.
  • The lock screen is not themed and was not tested: User Themes is not active while the screen is locked, and checking what happens on lock and unlock needs the owner's real session.
  • Installing User Themes through the Shell's own installer. The app says where to get it.
  • Coverage is the main surfaces: panel, overview, menus, dialogs, notifications, on-screen displays, search, dash. Buttons, sliders, the calendar's inner parts and the on-screen keyboard keep stock colours.
  • The remaining lines of the definition of done, above: the app's own window in stock colours, translation of the shared sentences, the manual checklist, GNOME 51.
