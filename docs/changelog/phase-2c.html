Phase 2c – theme editor, import and export

Branch phase-2c-editor. Completed 2026-10-12. The third slice of Phase 2 (D47). Its exit condition in the roadmap: a theme can be created in the GUI. It can, and the gate creates one in every run. With Phase 2a this meets the exit condition of Phase 2 as a whole; slices 2d and 2e remain.

On the owner's desktop nothing was changed. The editor was driven in a throw-away session; no theme was added to the real library.

Added

  • The editor. New Theme on the Themes page (Ctrl+N) starts from three colours: background, text and accent. Every other colour is worked out from those and shown, under Interface, Terminal and Code. Any of them can be given a colour of its own with the desktop's colour chooser, and sent back to automatic. The preview at the top follows every change. Save Theme (Ctrl+S) and Discard end it; while there are unsaved changes the page cannot be left by accident.
  • Hard to read, said in words, with Fix. Four pairs have to read: text and secondary text on the background, text on the accent, and selected text on the selection. A pair that does not is listed with its contrast and the contrast needed. Fix moves the colour lighter or darker, keeping its hue, until it reads.
  • Terminal colours for a new theme. Six hues at a lightness that reads on the background, and four neutrals taken from background and text. They follow the three main colours until one is changed by hand.
  • Edit, Duplicate to Edit, Export and Remove on a theme's page. A theme that comes with Velatura is edited as a copy. Removing one of the user's is done at once and offers Undo.
  • Import (Ctrl+O). The file is checked before anything is stored. The question shows the theme's colours, its name and author as plain text, and the sentence that theme files hold only colours and names and cannot run anything. If a theme with the same id is there already, the choices are Keep Both and, for a theme of the user's, Replace.
  • The command: velatura theme import <file> [--as <id>] [--replace], theme export <theme> [<file>], theme resolve <theme> (the theme with every colour written out) and theme remove <theme>, which keeps a copy and says how to put it back.
  • A theme written by the app has every colour written out, no references, and reads back as exactly the same theme. Text in it (name, author, description) cannot break out of its string.

Tests and checks

  • Eight tests of the editor's logic: themes from three colours are complete, valid and readable in light and dark; worked-out colours follow until made custom; a saved theme reopens knowing which colours were automatic; hard-to-read pairs are found and fixed; both bundled themes survive being written out and read back; hostile text in a name cannot add keys to the file.
  • Four tests of the library: save, replace, remove and put back; what comes with Velatura cannot be replaced or removed; an imported file is stored as it was written, comments included; a file that is not a theme (a script, binary data, too large) is refused before anything is stored.
  • The command end to end: import, the same again refused, under another id, applied, exported, removed and imported back.
  • In the gate: the app makes a new theme in the editor, changes colours until a pair is hard to read, fixes it and saves; the command then lists the theme as the user's.
  • 123 tests in all. The translation template has 318 strings.

Changed from the plan

  • The editor writes the whole file; it does not edit it in place (D51). The plan had the editor keep comments and unknown keys when saving. That needs a second TOML library that edits text. Instead, the first time the app saves over a file that was written by hand, the file as it was is kept beside it as <name>.toml.orig. An imported file that is not edited is stored exactly as it came.
  • Automatic colours are recognised, not recorded. A saved theme has every colour written out, as the plan requires. When it is opened again, a colour that is exactly what would be worked out counts as automatic, so it follows the main colours again.

Not done in this slice

  • One variant at a time. The editor edits the variant it was opened from and keeps the others as they are. Variants cannot be added or removed in the app.
  • Author, licence and description are kept but cannot be edited in the app.
  • The named palette of a hand-written theme is kept, but colours saved by the editor are written as values, not as references to it.
  • Diff and diagnostic colours and the per-app slots are kept and not shown; no target uses them yet.
  • Saving a theme that is in use does not apply it. Apply Theme on its page does.
  • Importers for other formats (base16, Kitty) are Phase 3.
  • Not checked by a person: the colour chooser and the file dialogs, which a headless session cannot open. Keyboard-only use and the screen reader in the editor are on the manual checklist.
