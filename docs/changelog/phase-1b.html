Phase 1b – more targets

Branch phase-1b-targets. Completed 2026-10-12. Exit condition from the roadmap: the transaction tests pass for each new target. They do.

On the owner's desktop only what was agreed on 2026-10-12 is applied: Aetherius on Kitty and the appearance settings (D39). The three new targets were exercised in throw-away folders and with the read-only preview. They are not applied until the owner says so.

Added

  • Ghostty. A colour file Velatura creates, velatura.conf, and a marked block at the end of Ghostty's settings file with the line config-file = velatura.conf. Either of Ghostty's two file names is used, whichever exists.
  • GTK 4 and libadwaita apps. ~/.config/gtk-4.0/velatura.css with 65 named colours, connected by an import line in a marked block at the end of gtk.css. The file holds colour definitions only: no selectors, so shapes and spacing cannot change, and nothing an older GTK would reject.
  • GTK 3 apps, through the adw-gtk3 theme: the same colour file in ~/.config/gtk-3.0/ and the legacy theme setting switched to adw-gtk3 or adw-gtk3-dark. The theme is looked for in the user's and the system's theme folders. Without it GTK 3 is left out with an explanation and does not count as a failure.
  • What would override the theme is reported for every target: lines after Velatura's block that set the same colours (Kitty, GTK), another config-file line (Ghostty), Kitty's automatic theme files, and a legacy GTK 3 setting that forces dark while a light theme is applied.
  • High Contrast. While it is on, GTK recolouring is left out, because the overrides would lower contrast. Terminals are not affected.
  • Other theming tools are listed by velatura doctor: Gradience, pywal, matugen, darkman, Night Theme Switcher, any enabled user timer with "theme" in its name, and the dotfile managers chezmoi, yadm and Home Manager. Detection looks only at whether their files exist; nothing is run.
  • Linked settings files are written through and the link kept, and the preview now says where the change really lands.
  • Hard-linked files are detected and left alone, since replacing one would split it from its other names.
  • Extended attributes (security label, access lists, tags) are carried over when a file is replaced.
  • Install script, scripts/install-local.sh: builds the command and copies it to ~/.local/bin. The owner's copy is refreshed after every merge.

Checked by hand, in a throw-away settings folder on libadwaita 1.9.4: a libadwaita app resolves the generated colours, and they win over definitions earlier in the same gtk.css.

Changed from the plan

  • Ghostty is connected with config-file, not with a theme file and a theme line (D41). Ghostty loads such a file after the whole settings file that names it, so its colours win over a theme line and over colour keys anywhere in the user's file. The planned method would have lost to both, and this machine's file has a theme line.
  • Agreement is asked only for a file that already exists. Creating a settings file where there was none is not an edit of the user's file.
  • A missing adw-gtk3 is treated like an app that is not installed: shown in the preview and in doctor, not repeated after every apply, and not a reason for exit code 5.
  • Dependencies: xattr was added for the attribute copying. The command links 44 third-party crates; the cap is 45.

Not done in this phase

  • The new targets are not applied on the owner's desktop. On this machine the preview shows Ghostty and GTK 4 ready, and GTK 3 left out because adw-gtk3 is not installed.
  • Colours that exist only as CSS variables in newer libadwaita are not set. Their names need checking against each libadwaita version first; until then those few elements keep the stock colour.
  • libadwaita 1.6 to 1.8 remain unverified; the check above was on 1.9.4. Phase 2, in containers.
  • A running app and an editor holding the file open are not detected.
  • Whether a dotfile manager actually manages a given file is not determined; its presence is reported.
  • Real fuzzing with a coverage-guided fuzzer, and a check of dependencies against a security advisory database. The mutation test and the licence check are the cheaper stand-ins.
  • Failure cases still untested: a really full disk, immutable files, a home folder that is itself a link.
  • A lint that forbids file access outside the host layer.
  • Flatpak apps see the GTK files only where an override already grants access (this machine has one). Managing that is Phase 2.
