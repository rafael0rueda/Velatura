Phase 4a – Firefox

Branch phase-4a-firefox. Completed 2026-10-14. The first of five slices of Phase 4 (D59). Its exit condition: Firefox passes the same transaction tests as the other targets, and a real Firefox draws its window in the theme's colours. Both hold.

On the owner's desktop nothing was changed. Firefox 157 is installed there; its list of profiles was read, and the stylesheets inside the program were looked at. Nothing was written into ~/.mozilla. Everything else ran in throw-away home folders, with a headless Firefox of their own.

What looking at Firefox showed

QuestionResult
How does Firefox colour its own window?From design variables declared on the root of the window: --toolbox-background-color for the tab strip, --toolbar-background-color, --toolbar-field-background-color, --panel-background-color and so on. On Linux their defaults come from GTK's header bar and window colours. A Firefox theme sets the same ones through a map Firefox keeps.
Does a stylesheet in userChrome.css win over Firefox's own?Only with !important: it is a user stylesheet, and the cascade gives Firefox's ordinary declarations the last word over a user's. With it, the variables win over Firefox's defaults and over a Firefox theme.
Which profile does Firefox open?The one installs.ini names for its installation. Here that is w6hrzc8i.default-release, while profiles.ini marks another, older one Default=1: going by that mark alone would have themed a profile Firefox never opens.
Can "Firefox is running" be told reliably?No. Its lock file here pointed at a process that had ended two days earlier. Waiting for Firefox to close would have kept the schedule from reaching it most of the time (D60).
Can a test ask Firefox what it drew?Yes. Started headless with Marionette, Firefox answers questions asked in its own window's context: the colour each part is drawn in, and each variable's value.

What it does

  • A part of its own, off until turned on: Firefox, on Apps & Desktop under Apps, marked as unofficial; firefox in the command. Its first change needs agreement, as Flatpak Apps' does: the profile is the user's, and a scheduled switch never starts theming Firefox by itself. After that it follows every apply and switch.
  • Three things in the profile Firefox opens by default: a stylesheet of Velatura's own, chrome/velatura.css; a marked block at the top of chrome/userChrome.css that imports it, since an import has to come before every rule; and a marked block at the end of user.js that turns on toolkit.legacyUserProfileCustomizations.stylesheets, without which Firefox does not read userChrome.css. Rules and lines of the user's in both files stay where they are, through apply and undo.
  • The stylesheet sets 39 of Firefox's design variables, and the colour scheme, on the root and nothing else: the tab strip, toolbar and its buttons, the address field and its results, menus and panels, the sidebar, and the accent for buttons, focus rings and links.
  • Written while Firefox runs. It reads these files only when it starts and never writes them; its own prefs.js is never touched. The result says that Firefox shows the change after it is restarted.
  • Where profiles are looked for: ~/.mozilla/firefox, then ~/.config/mozilla/firefox, then the Flatpak's and the Snap's folders. A profile path that would lead out of Firefox's folder is not followed.
  • What is reported: that other profiles are left as they are; rules of the user's that set the same variables after the import, and a line after the block that turns the preference off, both of which win; and after Undo or Remove Everything, that Firefox keeps the preference in its own settings, with the setting to change in about:config to turn it off.
  • Left out, with the reason: no Firefox; a Firefox that has never been started and so has no profile; a file named velatura.css that is not Velatura's.

Tests and checks

  • Seven transaction tests in tests/firefox.rs, with a profile folder as Firefox leaves it: off until turned on, and with no one present nothing is written until agreed; apply, the same again (nothing), another theme (the stylesheet only), and two undos back to the exact start; the user's rules and lines kept through undo and Restore Original Setup; rules and lines that win are reported; a crash at every step, from a clean home and an applied one; where profiles are found (none, a list that names none or one outside, an older Firefox, the Flatpak's folder, a profile by its whole path); a file of that name that is not Velatura's.
  • Unit tests for reading Firefox's ini files, for profile paths that may only lead down, and for telling a variable from a longer one with the same start. A block test for the import at the top and the preference at the end.
  • A golden file per bundled theme; a check that the output is only important declarations on the root; damaged theme files rendered without anything but colours reaching it.
  • A test that every variable is one Firefox's own stylesheets read, against a list taken from Firefox 157 by scripts/firefox-variables.sh.
  • In the gate, against a real Firefox: scripts/firefox-accept.sh has the command apply Ember in a throw-away home, starts Firefox headless on that profile, and asks it for the colour of the window, the tab strip and the toolbar, and for the value of each variable. After Undo the three files must be gone and the toolbar drawn in Firefox's own colour. Without the line in user.js the check fails, as it should. CI installs Firefox on the two newest Fedora releases.
  • 196 tests in all. The translation template has 392 strings, all in Spanish.

Changed from the plan

  • The default profile only, not "each chosen profile" (D60, accepted by the owner on 2026-10-14).
  • Written while Firefox runs, where the plan said nothing is written then (D60, accepted by the owner on 2026-10-14).
  • Off until turned on, which the plan did not say (D60, accepted by the owner on 2026-10-14).
  • Phase 4 is in five slices, and releases are on GitHub only (D59).

Not done, and what only a person can do

  • Not looked at by a person. Firefox was asked what it drew, headless; how the window reads, in a real session and next to the rest of the desktop, needs a person. That is part of the owner's full test of the app.
  • Two versions checked: Firefox 157 on the owner's machine and Firefox 158 in the Fedora 44 container, which both drew their windows in the theme's colours. CI checks the Firefox of Fedora 44 and 45 from now on; the list of variables was taken from 157. Firefox renames variables now and then: a renamed one stops working without an error, and shows up as a failing test once a new list is taken.
  • Web pages keep their own colours. Only Firefox's window is themed, not pages, Firefox's own pages such as the new tab page included.
  • Several Firefox installations (release and Nightly, say) share one list of profiles; the first one listed is the one themed.
  • The Flatpak and Snap folders were tested in throw-away homes only, not with a real Flatpak or Snap Firefox.
