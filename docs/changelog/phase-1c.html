Phase 1c – the app

Branch phase-1c-gui. Completed 2026-10-12. Exit condition from the roadmap: the first apply takes four interactions or fewer. It takes three: open a theme, Apply Theme, confirm.

The window was never opened on the owner's desktop. It was run in a headless session with a throw-away home folder and its own settings database, and the pictures below were rendered there. How it looks and feels in real use is for the owner to judge.

Added

  • The app, velatura-app: a libadwaita window using only what libadwaita 1.6 offers. It reads and changes nothing itself; every operation is the same engine call the command makes, run off the main thread.
  • Themes. A list with a strip of each theme's colours, the theme in use first and marked in words and with a check mark. A theme's page shows a preview, the style, the system accent it maps to, the text contrast, and one button.
  • Preview. Real buttons, a switch and text wearing the theme's colours, scoped to the preview alone, and a drawing of a terminal with the sixteen terminal colours. Captioned as an illustration.
  • Apply, as decided in D37: a confirmation in plain words the first time and whenever a settings file would be edited for the first time; otherwise the theme is applied at once and a message offers Undo. The exact changes are behind Show Details.
  • A theme with low text contrast always asks, with the button reading Apply Anyway, styled as destructive and never the default.
  • Result page when there is something to know or do afterwards: which apps need reopening or a key press, what was left out and why, and Undo.
  • Apps & Desktop. One row per part, grouped as Desktop, Terminals and Apps, each with its state in words and one switch that includes it in or leaves it out of future applies. A part that cannot be themed is greyed out with the reason. Remove Everything Velatura Added is done at once and offers Undo.
  • History. Every backup with what it was and when; Restore goes back to just before it, after one confirmation, because several steps cannot be reversed with a single Undo.
  • Troubleshooting: each part's state, other tools that change colours, and the command to run from a text console if the desktop becomes unreadable.
  • Banners for the two lasting states: an interrupted change, with a Roll Back button, and High Contrast being on.
  • Narrow windows: below 550 points the view switcher moves to the bottom edge. Minimum size 360×294.
  • Keyboard: Ctrl+Z Undo Last Apply, Ctrl+W, Ctrl+Q, F10, Ctrl+?, Alt+Left, all listed in the Keyboard Shortcuts window. Access keys on the menu items, view names and buttons.
  • Translation scaffolding: every string of the app goes through one lookup function; scripts/update-pot.sh collects them into po/velatura.pot (114 strings, plural forms included), and the gate fails if that file is out of date.
  • App icon, symbolic icon and launcher; scripts/install-local.sh now installs the app, its launcher and its icons for the user.
  • In the engine: the per-part "include" choice, restore-to-a-backup as one call, and the remembered window size. The command honours the same choices; naming a part with --only overrides having turned it off.

Tests and checks

  • The main flow, through the real window, in every local gate run: the app starts in a throw-away session, applies a theme, the confirmation appears and is accepted, then Undo is activated; after each step the state and the files in the sandbox are checked. This step needs a headless compositor and does not run in CI.
  • The app is built and linted in CI, and its plain-language summary and the new engine calls have unit tests. 77 tests in all.
  • Looked at by rendering: all views at the default size, at 360×560, and mirrored for right-to-left.
  • The launcher file is validated by the gate.

Changed from the plan

  • The interface is built in Rust code, without Blueprint, and the build is Cargo alone, without Meson (D43, for the owner to accept or reverse). One build command, no extra build tools, and the compiler checks the interface code. Meson is still needed for a proper installation with translations and store data, and comes with packaging.
  • Apps & Desktop rows do not open a page per app, as correction H3 of the interface guidelines described. A row has its state and one switch. Stopping the theming of a single part needs an engine operation that does not exist yet.
  • History's Restore asks first, where most actions offer Undo instead: it reverses several changes at once.

Not done in this phase

  • The app's own window is not kept in stock colours. Once a theme is applied to GTK 4 apps, Velatura wears it too after a restart, as the pictures taken after an apply showed. A badly made theme could therefore make the app hard to read. The low-contrast confirmation and the console command are the safeguards for now.
  • The "Keep this theme?" countdown that reverts a low-contrast theme unless confirmed.
  • Translations are not loaded yet. The strings are collected and the lookup is in place, but the catalog is only found once the app is installed with its data, and the sentences shared with the command (the change list, reasons, hints) are English only.
  • Stop Theming for a single part, theme search, Preferences, Help, a copy button for commands, and a banner when the accent or style is changed elsewhere.
  • Store data (the metainfo file) and a nightly icon: with packaging.
  • Accessibility testing, as line 12 above says.
  • Start-up time and memory of the app were not measured.
