Phase 3a – tmux, Neovim and Starship

Branch phase-3a-cli-apps. Completed 2026-10-13. The first of four slices of Phase 3 (D54, which also leaves Obsidian out of the project). The exit condition of Phase 3 applies to each target: it passes the same transaction tests as the others. The three in this slice do.

On the owner's desktop nothing was changed. The three apps were run in throw-away home folders. What applying would do there was looked at with copies of the owner's settings; see the last section.

Added

  • tmux. A file of Velatura's own, ~/.config/tmux/velatura.conf, sets the colours of the status line, the window list, pane borders, messages, copy mode and the clock: fourteen options that tmux has had since version 2.9. One line in a marked block at the end of the user's settings loads it: source-file -q ~/.config/tmux/velatura.conf. With -q, tmux says nothing where the file is not there, as on another machine that shares the settings. The block goes into the file tmux reads last: tmux.conf in the settings folder, or ~/.tmux.conf when that is the only one.
  • Neovim. A colourscheme that stands by itself, ~/.config/nvim/colors/velatura.lua: about 160 highlight groups for the editor, code, Tree-sitter, diagnostics, changes and about ten widely used plugins, and the sixteen terminal colours. No plugin is needed. Beside it, lua/velatura/palette.lua gives the same colours as a table, for people who keep a colourscheme of their own: require("velatura.palette"). Nothing of the user's is edited; choosing the colourscheme stays theirs, and the result says how.
  • Starship. The palette velatura, with the seventeen interface colours and the three slots a theme can set for the prompt (directory, git, language), and the line that selects it. Starship cannot load a second file, so these lines go into starship.toml itself, in a marked block at its top. The prompt shows a colour only where its settings name one.
  • Colours a theme does not give. Code, diagnostic and changed-line colours are optional in a theme. Where one is missing it is taken from the terminal and interface colours, so every theme gives a complete Neovim colourscheme, a theme made in the editor included.
  • In the app, a group Command-Line Apps on Apps & Desktop, with a switch for each. In the command, tmux, nvim and starship for --only and --except, and in velatura targets.
  • What is reported. Lines after the block in tmux's settings that set the same options and so win; that running tmux sessions keep their colours until the settings are loaded again, with the command; and for Starship and Neovim what the user has to do for the colours to show.

What the apps showed

QuestionResult
Does tmux read both ~/.tmux.conf and the file in its settings folder?Yes, in that order (tmux 3.7), so the second has the last word. The block goes there when it exists.
Can the palette sit at the top of starship.toml, before the user's own tables?Yes, written as keys of the file's root with dots (palettes.velatura.accent = …). Tables that follow, other palettes among them, still read. A table header at the end of the file could hold the palette but not the line that selects it, which must come before the first table.
What if the file already selects a palette?Its prompt is written for that palette's names, and a second palette line would make the file invalid. Velatura leaves the file alone and says why.
Is a Lua table key always a plain word?No: function is a word of the language. The table writes its keys in brackets.

Tests and checks

  • Nine transaction tests for the three targets in tests/cli_apps.rs: apply, apply again (nothing changes), another theme, and two undos back to the exact start; a crash at every step, from a clean home and from an applied one; lines the user wrote since are kept by undo; apps that are not installed are left out; tmux's two files; a settings folder whose name tmux could misread; files in Neovim's folder that are not Velatura's, or were edited; Starship settings that select a palette, define velatura themselves, or do not read; STARSHIP_CONFIG, inside and outside the home folder.
  • One test for a marked block at the top of a file: added and taken out byte for byte, with Windows line endings and a byte order mark.
  • Golden files for the four generated texts of each bundled theme. The damaged-theme test now sends every theme that loads through the new renderers too.
  • The apps accept them. scripts/apps-accept.sh, part of the gate: tmux loads each file and shows the option; Neovim loads the colourscheme twice and computes the colours of the file, and reads the table; Starship renders a prompt that names two of the palette's colours, without a warning. tmux and Neovim are required in CI. Starship is not packaged for the CI image, so there it is checked on the development machine only.
  • 152 tests in all. The translation template has 365 strings, all in Spanish.

Changed from the plan

  • Phase 3 is built in four slices (D54), as Phases 1 and 2 were.
  • Starship's lines are a marked block, not a key-level edit (D55). The plan had single keys added to the file, as for Flatpak. A block at the top does the same with the mechanism the other targets use: undo finds it by its markers and takes it out of the file as it is then.
  • Neovim gets the colourscheme and the table, not one or the other. The plan offered the table "instead", for people with their own colourscheme; a choice would need a setting, and the second file costs nothing.
  • The first files in an existing Neovim folder need agreement (D55), although no file of the user's is edited. Otherwise a scheduled switch, with no one present, would put files into that folder the first time this version runs.
  • The agreement wording is wider. "Adding a line to a settings file" became "adding to the settings of an app", in the command's help and in the reason shown when it was not agreed to.

Not done, and what only a person can do

  • On the owner's machine, Starship is left out. Its starship.toml selects a palette of its own, aetherius, and the prompt is written for that palette's names. To have the prompt follow the theme, the prompt has to name Velatura's colours and drop its own palette line; that is the owner's file to change.
  • The owner's tmux settings set colours inside status-left and status-right, as text. Velatura sets the styles around them, not the text of those two, so those segments keep their colours until they are written without fixed ones.
  • Neovim: the look was not judged by eye. The check is that Neovim loads the file and computes its colours. Whether code reads well in both bundled themes needs a person in an editor.
  • NVIM_APPNAME and other settings folders of Neovim's are not looked for; only ~/.config/nvim.
  • tmux plugins that draw the status line (themes installed through a plugin manager) set their own colours when they load, and may win. They are not detected.
  • Applying these three on the owner's desktop was not done: it needs the owner's go-ahead.
