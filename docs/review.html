Review findings

Five read-only reviewers examined revision 1 of the plan on 2026-10-11, one perspective each. This page records what they found, what changed in revision 2, what was not adopted, and what is still open.

The reviewers raised 22 blockers and about 175 findings in total. None of the blockers invalidates the project; each is resolved in revision 2 by a design change, moved to a Phase 0 spike, or listed below for the owner's answer. Claims the reviewers marked as verified were checked by them against this machine or upstream source code. The ones marked "re-checked" I confirmed myself afterwards; the others rely on the reviewers' evidence and have not been independently confirmed.

4. Not adopted, or adopted only in part

  • Drop cursor and bitmap icon recolouring (Architecture). Kept as Phase 4 experiments, because the owner asked for recolouring. Listed above for confirmation.
  • Move wallpaper and fonts to Phase 4 (Architecture). Kept in Phase 2: they are single settings and the owner asked for them.
  • A login-time job that resets the Shell theme after an upgrade (Safety). Not needed once the theme is overrides only. A version stamp and apply --if-stale remain.
  • A bus-activated background service shared by timers, GUI and extension (Packaging). Deferred; the timer runs the CLI directly. Revisit if a sandboxed build is made.
  • One usability test with a non-expert before the MVP (UX). Recommended, not made a formal exit condition.
  • A single apply that fails as a whole on any precondition was the original design; the review replaced it with per-target skipping, which was adopted.

5. Open questions for Phase 0

Each is a small throw-away experiment. The plan is corrected where an assumption fails.

  1. GTK connection that wins. Where can the connection sit in gtk.css so the theme takes precedence over definitions already in the file, without touching the user's lines? Does an import resolve when gtk.css is a symlink, and inside a Flatpak sandbox?
  2. libadwaita 1.6 to 1.9, and older Flatpak runtimes. Same precedence as verified on 1.9? Do older GTK versions skip an unknown media query cleanly?
  3. The app immune to theming. Can the app's own window keep stock colours regardless of the user's gtk.css, on each libadwaita version?
  4. Preview with real widgets. Can a part of the window be given its own colours reliably?
  5. Shell overrides. Behaviour in light, dark and High Contrast on 50 and 51; a lock and unlock cycle; what a malformed stylesheet does; cleaning up old theme folders.
  6. Installing User Themes through the Shell, including when extension installation is disabled and when offline. Reading its schema from Rust without the process aborting.
  7. adw-gtk3. Does it take colour overrides from the user's gtk.css? Per-user install; behaviour with High Contrast.
  8. Kitty. Which version added automatic config reload, and does it watch included files?
  9. Exact undo. Settings unset versus default; list-valued settings; created directories; symlinked configs; security labels after restore.
  10. Role sufficiency. Write the GTK, Kitty and Neovim outputs for Aetherius by hand from the proposed roles and compare with the current desktop.
  11. Rust measurements. Binary sizes, crate count, start time and memory of a switch, build times, and the owner's own speed on one GUI screen. Icon recolouring speed against a plain Python baseline.
  12. Translation tooling for Rust sources on the CI image.
  13. Compiling the Shell's style sources with a Rust SASS compiler, as the route to exact accent and full coverage.
  14. Related work. Look at gtheme and Rewaita.
  15. Sandbox check (only if a Flatpak build is wanted): can host settings be written from inside one?

6. Main findings by reviewer

GNOME/GTK platform

  • Blockers: the Shell theme must be overrides only; re-applying the same theme name does not reload the Shell.
  • Extension stylesheets always outrank the user theme. The Shell accent cannot be set by simple overrides.
  • User Themes is installed here but disabled; its schema is not on the default path; the lock screen is not themed at all.
  • The GTK3 fallback is a no-op. An import at the top of gtk.css loses to definitions below it.
  • Colour-scheme media queries need GTK 4.20; Flatpak apps use their runtime's GTK.
  • Kitty's automatic theme files override everything and cannot be app-owned. Ghostty has two config file names.
  • Icon sets in ~/.local/share/icons are already visible to Flatpak apps.
  • X11 app title bars pick up gtk.css only at login. GNOME 50 has no nested Shell mode for testing.
  • Forgotten areas: Ptyxis, GNOME Text Editor, the legacy settings.ini dark preference, the desktop portal.

Safety and reliability

  • Blockers: blind crash recovery; plans going stale between preview and apply; missing settings schema aborting mid-apply; an under-defined "original" snapshot; the active old timer; existing settings making the MVP a no-op; theme strings reaching generated files; no unattended policy; stale Shell theme after an upgrade.
  • Durability order (what is synced and when) was unspecified. Rename loses extended attributes, access lists and security labels.
  • Symlinks: dotfile tools, links leaving the home directory, /home itself being a link.
  • Drift must be measured on the app's span only, or every user edit triggers a prompt.
  • Marker grammar, byte fidelity and element-level undo were unspecified.
  • Backup store: integrity checks, safe pruning, size growth from icon sets, privacy.
  • Firefox's preference is not reversible by removing the line.
  • A long list of missing failure tests, now in the test plan.

UX/UI

  • Blockers: the first-run flow was too long; the app itself would be recoloured into unreadability; the minimum-version claim was not achievable; High Contrast had no mechanism; nothing prevented applying an unreadable theme.
  • Target state in two places; no indication of the theme in use; theme and variant names colliding.
  • Internal vocabulary leaking into the interface; three inconsistent badge sets.
  • Day and night confused with dark style and Night Light.
  • The only Undo was in a transient message. Failure and conflict messages were undesigned.
  • Editor too large; import and trust prompt undesigned.
  • CLI vocabulary differed from the GUI; disconnect with no argument was dangerous.

Architecture and maintainability

  • Blockers: the format could not carry the existing palettes; "pure planners" was not achievable; per-version Shell overrides are the largest recurring cost; the MVP was too large.
  • The language comparison overstated Rust and omitted velocity, testability and release cost.
  • Derivation must be versioned or users' themes change silently.
  • Multi-instance targets had no place in the model. The change list was incomplete.
  • No host abstraction was defined, though tests and distribution both depend on one.
  • Persisted formats need versions; the backup manifest is the longest-lived interface.
  • Estimated upkeep: two to five days per GNOME release for Shell overrides, twice a year.

Packaging and distribution

  • Blocker: a full-fidelity Flathub release is unrealistic, for permission and policy reasons.
  • Host settings written from a sandbox can fail silently. Timers and the CLI are awkward from a sandbox.
  • State must live in one place across install channels.
  • Bundled data should be compiled in. Crate names, minimum compiler version and vendoring should be fixed early.
  • Immutable desktops have no dnf install; per-user installs must be the primary advice.
  • The extension belongs on extensions.gnome.org, with its review rules in mind.
  • The application ID fixes many other names and must be chosen before the repository exists.
